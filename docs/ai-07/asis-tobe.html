As-Is→To-Be

AI駆動開発は、開発工程のどこを・なぜ・どれだけ変えたか

「通常の開発フロー（As-Is）」と「AI駆動開発（To-Be）」を工程ごとに並べて、 どの作業が消え／縮み、どの作業が人の手元に残るのかを可視化する。 AI開発をブラックボックスにせず、説明可能な運用モデルとして提示する資料。

03
カテゴリ A ／ データモデル設計・実装

「設計書を書いてから実装」の2段階が、型からの1発生成に

As-Is ｜ 通常開発112h
1テーブル設計書を作成（ER・カラム定義）
2設計レビュー・修正の往復
3Prisma schema を手で実装
4migration 作成・適用
→
To-Be ｜ AI駆動開発4.4h
1spec＋ER／型定義を入力として渡す人
2DBアーキテクトAIが schema＋migration を直接生成AI
—設計書という中間成果物
—設計レビューの往復
決定的な削減ポイント
型定義・ER が入力に揃えば、「設計書を書く→実装する」の中間ドキュメントと設計レビューの往復が丸ごと消える。AIは型を直接スキーマに変換する。
112h → 4.4h
約 96% 削減
カテゴリ A：データモデル
04
カテゴリ B ／ IF（API）設計・実装＋単体テスト

入出力が型で決まる領域は AI の独壇場。テストは実装に内包

As-Is ｜ 通常開発217h
1API設計（エンドポイント・DTO設計）
2CRUD／ページング／フィルタ／例外処理の実装
3単体テスト設計（観点出し）
4単体テスト実装（合計 61h）
→
To-Be ｜ AI駆動開発8.8h
1型定義・DTO で入出力を確定人
2バックエンドAIが API実装と単体テストを一括生成AI
—単体テストの独立工程
—CRUD の定型実装
決定的な削減ポイント
「入力（検索条件）」と「出力（プロパティ）」が型で決まる領域は、ロジックがほぼ一意に定まる＝AIが最も正確に書ける。単体テストは実装に内包され、独立工数がゼロになる。
217h → 8.8h
約 96% 削減
カテゴリ B：IF／API
05
カテゴリ C ／ 画面処理（UX設計・画面設計・実装）

mock が UX仕様の正本になり、「mock → 実装」の一気通貫に

As-Is ｜ 通常開発337h
1UX設計（画面遷移・レイアウト方針）
2画面設計書（コンポーネント設計）
3一覧／検索・入力フォームの実装
4状態遷移・ドロワー・モーダルの実装
→
To-Be ｜ AI駆動開発14.4h
1mock（クリッカブルモック）＋spec を入力人
2フロントエンドAIが UX・設計を内包して実装AI
—UX設計書・画面設計書の作成
✓mock との視覚差分は人が確認人
決定的な削減ポイント
mock がそのまま UX仕様の正本になることで、「UX・設計書 → 実装」が「mock → 実装」に短絡。設計工程が実装へ吸収され、最も工数の大きい領域が 1/25 以下に。
337h → 14.4h
約 96% 削減
残る課題：mock の grid 配置など視覚情報が実装で落ちるケースがあり、視覚差分の検証は人の動作確認で担保する必要がある。
カテゴリ C：画面処理
06
カテゴリ D ／ 検証・レビュー・調整（人の領域）

あえて削らない工程＝ここが納品品質の砦

AIが書いたコードを人が保証・調整する工程は削減されない。実装側は縮むが、保証・調整は人側に残り続ける。

APIレビュー（エンジニア）14.8h → 14.8h
AIが書いたコードを人が同じ密度でレビュー。As-Is と工数は完全に同一。
動作確認（BE＋FE）13.7h → 11.6h
実機での確認・mock視覚比較。AIに委譲できず、人の目視が品質の最終ゲート。
フロントレビュー（エンジニア）5.3h → 5.1h
画面コードのレビューも人が担保。生成量に関わらず確認密度は変わらない。
AI出力後の調整（レイアウト・API最適化等）0h → +11.0h
AI生成物の細部調整・最適化として新たに発生する人の工程。大半がエンジニア工数。
合計でみると 約 33.8h → 約 42.5h でむしろ微増。AIの削減効果はこの「保証・調整」工程には及ばない —— だからこそテスト観点を「納品品質の物差し」に再定義する議論につながる。
カテゴリ D：人の領域

この進め方を前提とすれば、実装は 1/25 以下・保証は人が担保

結論：型・mock・spec が揃う「AIと相性の良い領域」から局所的に積み上げる。実装工数は劇的に縮み、品質保証は人が担保する —— これが再現可能な運用モデル。
