01 あるある

仕様が変わるたび、if が増えていく

「条件を1つ足すだけ」のはずが、毎回 分岐の組合せ・順序・抜け漏れ に悩む。テストも一緒に壊れる。機能追加のコストが、機能数に比例せず 指数的に膨らむ ― なぜ？

function handle(req) { if (req.type === "A") { /* ... */ } else if (req.type === "B") { /* ... */ } else if (req.type === "C") { /* ... */ } else if (req.type === "D") { /* ← 今日もまた一行 */ } // ...そして誰も全体を読めなくなる }

1本足す・順序を変えるだけで 後続の分岐すべての挙動が変わりうる。影響がその行に閉じないのが厄介。

02 問い

仕様は「定義」で書かれている

How — 手順

手続き

「まず◯◯、次に△△、もし□□なら…」
＝計算をどう実行するか。知識が制御フローに溶ける。

What — 定義

定義

「正しい入力とは／価格とは／状態とは」
＝対象が何であるか。知識がデータとして外に出る。

仕様書は 定義（What） で書かれるのに、コードは 手続き（How） で書きがち。このズレが変更を難しくする。定義をデータで表し、解釈する汎用の仕組みを1つ用意する ― これが 宣言的プログラミング（SQL・正規表現・CSS・React）の核。

03 なぜ強いのか

変更の局所性

Δ仕様≈Δコード

コードの構造を 「定義」の構造 に合わせると、
仕様の 1つの変更 が、コードの 1箇所 に対応する。

保守性の正体は、仕様の1変更がコードの1箇所に収まるか。

逆に手続きへ定義を埋め込むと、仕様を1つ変えただけでも 影響が1箇所に収まらず、手順のあちこちに波及する。これが指数的コストの原因。

04 例1 · FizzBuzz — 仕様追加: 7の倍数 → "Bazz"

同じ変更、ぜんぜん違う影響

手続き
if (i % 105===0) print("FizzBuzzBazz"); else if (i % 21 ===0) print("FizzBazz"); else if (i % 35 ===0) print("BuzzBazz"); else if (i % 15 ===0) print("FizzBuzz"); else if (i % 7 ===0) print("Bazz"); else if (i % 3 ===0) print("Fizz"); else if (i % 5 ===0) print("Buzz"); else print(i);
分岐が 4 → 8 に倍増。組合せ（21, 35, 105…）を手で網羅し、順序も並べ替える必要がある。
変更 = 分岐の作り直し / 抜け漏れ注意
定義
const rules = [ { divisor: 3, word: "Fizz" }, { divisor: 5, word: "Buzz" }, { divisor: 7, word: "Bazz" }, ]; // ↓ この定義を動かす本体（変更不要） const out = rules .filter(r => i % r.divisor === 0) .map(r => r.word).join("") || i;
「Fizz とは何か」を定義するので、組合せは定義から自動で導かれる。本体には手を入れない。
変更 = データに +1 行

定義（データ）と解釈する1つの汎用ロジックを分離 ― 仕様追加はデータに1行、ロジックは不変（21=FizzBazz 等の組合せも自動）。

05 例2 · 入力バリデーション

ルールを「スキーマ」として定義する

手続き
function validate(form) { if (!form.email) return "メール必須"; if (!isEmail(form.email)) return "メール形式が不正"; if (form.age == null) return "年齢必須"; if (form.age < 0) return "0以上で"; // 項目が増えるたび関数が伸びる… }
検証ルールが手続きに散在。項目追加・順序・国際化で関数が肥大化する。
定義
const schema = { email: [required(), pattern(EMAIL)], age: [required(), min(0), max(150)], name: [required(), maxLen(40)], }; // 汎用バリデータが schema を解釈 const errors = validate(form, schema);
仕様 = スキーマ。項目やルールの増減はデータ編集で済む。Zod / JSON Schema はこの発想の製品化。

スキーマはそのままフォーム生成・APIドキュメント・型にも使い回せる。定義が単一の真実の源になる。

06 例3 · 状態遷移

同じ「マトリクス」を、手続き と 定義 で表す

マトリクス＋型 · 仕様
state＼eventpaycancelshipdeliverreturnReq
draftpaidcanceled···
paid·canceledshipped··
shipped···done·
done····returned
returned·····
canceled·····
// 表を型で固定（中央・右で共用） type State = "draft"|"paid"|"shipped" |"done"|"returned"|"canceled"; type Event = "pay"|"cancel"|"ship" |"deliver"|"returnReq"; type Table = Partial<Record<State, Partial<Record<Event, State>>>>;
行＝状態、列＝イベント、セル＝次の状態。表と型が唯一の仕様 ― 中央・右はこれを写す。
手続き · imperative
function next(s: State, e: Event): State { if (s==="draft" && e==="pay") return "paid"; if (s==="draft" && e==="cancel") return "canceled"; if (s==="paid" && e==="ship") return "shipped"; if (s==="paid" && e==="cancel") return "canceled"; if (s==="shipped" && e==="deliver") return "done"; if (s==="done" && e==="returnReq") return "returned"; return s; // それ以外は現状維持 }
セル1つ = 分岐1本。状態×イベントの数だけ if が増える。順序・抜け漏れも人手で管理する。
定義 · declarative
const table: Table = { draft: { pay: "paid", cancel: "canceled" }, paid: { ship: "shipped", cancel: "canceled" }, shipped: { deliver: "done" }, done: { returnReq: "returned" }, }; function next(s: State, e: Event): State { return table[s]?.[e] ?? s; // 表を引くだけ }
型付きの表そのもの。遷移追加 = 行/列に1要素。表に無い状態・イベントはコンパイルエラー。

同じマトリクス（左）を手続き（中）と定義（右）で表現。State/Event を型で固定したので両方とも引数・戻り値が型安全。手続きはセルの数だけ分岐が要り、定義は表を写すだけ ― 表に無い状態・イベントはコンパイルで弾ける。

07 原則と注意

定義に寄せる ― 道具と、引き際

使う：定義に寄せる道具

  • データ / 表駆動 ― 知識をデータに出し、解釈する汎用の仕組みを1つ
  • 宣言的に ― How でなく What（SQL・正規表現・CSS の発想）
  • 仕様の語彙に合わせる ― 仕様の一文がコードで探せる
  • 型で表す ― 不正な状態を表現不可能に（違反はコンパイルエラー）
  • SSOT（単一の真実の源）― 定義は一箇所だけに置く。コピーは必ずズレる

引く：やりすぎない

  • 過剰抽象 (YAGNI) ― 「たぶん要らない（You Aren't Gonna Need It）」。2個で不変の分岐に汎用エンジンは過剰
  • 間違った抽象は無抽象より悪い ― 合わない定義は将来の足かせ
  • 3度の法則 ― 同じ形が3回現れてからデータに切り出す
  • 可読性・デバッグ性 ― 間接化は追いにくさとのトレードオフ
変わる軸にだけ「定義」を。変わらない所は素直な手続きで。
08 見抜き方

レビューで使えるチェックリスト

  • 仕様書の一文が、コードの一箇所に対応しているか？
  • 仕様追加のたびに if/else が増えるなら、定義がコードに埋もれているサイン
  • 同じ形の分岐が 3回 出たら、データに切り出せないか検討
  • ありえない状態を、型やデータの形で弾けているか
  • 同じ定義が複数箇所にコピーされていないか（SSOT）
09 まとめ
手続きは「いま」を解く。
定義は「仕様」を解く。

コードを仕様の写像にすれば、
仕様変更は写像のまま、小さく一箇所に収まる。

10 前提

第1部の論拠は「人間の保守性」だった

変更の局所性も、不正な状態の排除も、根拠は 「人間が読み・直し・壊さない」 ため。では、コードの多くを AIが書く なら、この話は変わるのか？

AI駆動開発は 定義型を相対的に有利にする。ただし理由が変わり、油断すると逆に手続きが増殖する。
11 核心

ボトルネックが移動する

人間が手で書く時代
書く
直す
AIに任せる時代
書く
意図を伝える
出力を検証する

「書く」コストは縮み、重心は 意図を伝える と 出力を検証する へ移る。そして、このどちらも 定義型に味方する。

12 含意 ①

定義型が効く、二つの局面

Tell — 伝える

宣言 = 仕様 = 良い指示

型・スキーマ・ルール表は、そのまま仕様であり、AIへの曖昧さの少ない指示になる。手続きを言葉で説明するより速く正確。

const schema = { age: [min(0), max(150)] }
Verify — 検証する

目視で照合できる

ルール表は仕様書と突き合わせて確認できる。手続きは実行を追わないと正しさを判断できない。委譲が増えるほど「検証の安さ」が効く。

人間時代の論拠は「直しやすさ」。AI時代の論拠は 「伝えやすさ」と「確かめやすさ」 に移る。

13 含意 ②

機械可読な定義は、AIの自己修正ループになる

定義
型・テスト・網羅された状態
生成›
AIが実装
手続きを書く
検査›
型エラー / 失敗
違反が機械的に弾かれる
修正›
AIが直す
自分で再試行
↻ パスするまで、人手を介さず反復できる

「不正な状態を表現不可能に」しておくほど、AIの間違いはコンパイルエラーで止まる。ガードレールが厚いほど、エージェントは自律的に走れる。緩い手続き型は、この信号が乏しい。

14 含意 ③ · 第1部の「あるある」再び

AIは「もう1つ if を足す」を、最もやりがち

手続き
if (t === "A") handleA(req); else if (t === "B") handleB(req); else if (t === "C") handleC(req); else if (t === "D") handleD(req); // AIがまた継ぎ足す
エージェントはターンごとに局所的なプロンプトで動く。全体を見て定義へ寄せるより、目の前に分岐を足す。
第1部の失敗を高速に再生産
定義
const handlers = { A: handleA, B: handleB, C: handleC, D: handleD, }; handlers[t]?.(req);
定義中心の構造なら、同じプロンプトでもAIの手は「データに1行」へ向かう。アーキテクチャがAIのお行儀を決める。
変更 = データに +1 行

そもそもAIは周囲の既存コードのスタイルに倣う ― 手続き的なコードには手続きを、定義的なコードには定義を足す。だから「定義に寄せる設計」はAI時代にこそ効く。良い構造が、AIを良い変更へ誘導する“レール”になる。

15 反対側

ただし、過剰抽象の罠は増幅する

!

AI製DSLがブラックボックス化

AIはDSL/ルールエンジンを即生成できるが、定義もエンジンもAI製だと誰も中身を読めない。平たい手続きの方が監査しやすいことも。
※ DSL＝独自のルール記法＋解釈器（例: SQL・正規表現）

!

「間違った抽象」がより重い

間違った抽象は無抽象より悪い ― 第1部の警句がAI時代に重みを増す。

!

修正コストも下がった

「直すのが面倒」という抽象化の動機の一部を、AIが消してしまった。

安く作れることと作る価値があることは別 ― 抽象は「安いから」ではなく「必要だから」作る。
16 結論

問いは「優劣」ではなく「境界」

手続き（How）AIが生成する · 再生成可能 · “使い捨て”の実装
定義（What）人間が所有・レビューする · 機械検査可能 · “耐久資産”
型スキーマルール表状態遷移表

仕様が変わったら ― 定義を直し、手続きはAIに書き直させる。守るべき中核と捨てられる外側を分ける。これがAI時代の設計の重心。最小抵抗経路は「とりあえず手続きを生成」なので、定義に寄せる規律は、人間時代よりいっそう意識的に持つ。

17 まとめ
AIが 手続き を安く書けるからこそ、
人間が握るべき資産は 定義 に寄る。

何を「定義」として耐久資産に持ち、
何を「手続き」としてAIに再生成させ捨てるか ― その線引きが本質。

仕様こそが、プログラム。

18 方針

「やる」と決めたら、問いは How に変わる

第1部は原則（なぜ定義か）、第2部はAI時代の含意（むしろ有利、ただし罠）。AI駆動開発で進めると決まったいま、必要なのは 「どう回すか」 の具体です。

第3部は ― 定義ファーストのAI駆動開発を、現場で回すためのプレイブック。
19 ワークフロー

1サイクルの回し方

人 ▸ 定義を更新
仕様・型・表を書き、所有する
生成›
AI ▸ 実装
手続きを生成・改修（使い捨て）
検査›
機械 ▸ 検査
型・テスト・CIが違反を弾く
確認›
人 ▸ レビュー
見るのは「定義の差分」
↻ 検査が通るまではAIが自律的に反復 ― 人手が入るのは両端（定義とレビュー）だけ

人手が入るのは定義とレビューの両端だけ。生成コードは直接いじらず（再生成できなくなる）、直すときは必ず定義側を直して回し直す。なぜこの分担になるかは第2部（境界）を参照。

20 定義の置き場

定義はどこに宿すか

仕様ドキュメント / ADR自然言語の定義。AIへの一次入力（ADR＝設計判断の記録）人が所有
リポジトリ規約CLAUDE.md 等。AIへの恒常的なルール人が所有
スキーマ型・実行時検証・ドキュメントを一枚で兼ねる常時検査
状態遷移表 / ルール表データとしての定義常時検査
テスト実行可能な仕様＝契約常時検査
型最も安く、常に効く定義常時検査

上ほど人が所有する自然言語、下ほど機械が常時検査する形式。機械検査可能な層に寄せるほど、AIの自己修正が効く。最上流の自然言語の定義は、形式の層とズレないよう一本化する。

21 初期投資

ガードレールは「先に」作る

A

厳しい型

any禁止・網羅性チェック。不正な状態を表現不可能にし、AIの間違いをコンパイルで止める。

B

契約としてのテスト

出力値でなく不変条件を縛る（プロパティ/契約テスト）。「通った」が「正しい」になる。

C

全チェックを通し切らせる

AIにlint・build・jest・cspell 等を実行し、エラーを全て解消してから完了と指示。CI任せにせず、生成のたびに手元で回し切らせる。

D

具体的な失敗メッセージ

失敗が機械可読で具体的なほど、AIは自分で直せる。曖昧な失敗は人を呼び戻す。

「ガードレールが厚いほどAIは自律的に走れる」を具体に落とした回。薄いガードレールの下では、AIは静かに間違える。

22 レビュー

人が見る場所が変わる

  • 見ているのは 「定義の差分」 か？手続きの差分は機械任せでよい
  • その手続きは、定義から決定的に導けるか？導けないなら、定義が不足しているサイン
  • 定義は 意図と一致 しているか？ここだけは、最後まで人間の仕事
  • 生成コードに 手で継ぎ足していない か？再生成可能性を壊さない
  • その抽象は 「3度」現れた実需 に基づくか？AI製DSLの過剰を弾く
23 境界の引き方 · 第2部を実務へ

その境界は、3つの質問で引く

第2部の境界（定義＝耐久資産 / 手続き＝使い捨て）を、目の前のコードに当てて判定する。

Q1

仕様変更の「軸」か？

よく変わる中心のロジックか。たまにしか触らないなら No。

Q2

同じ形が3度現れたか？

1〜2回ならまだ待つ。3度目で初めて切り出す。

Q3

表・スキーマで書けるか？

データとして外に出せる構造か。手順そのものなら No。

すべて Yes → 定義にする人が所有し、型・表で固定
ひとつでも No → 手続きでよいAIに素直に書かせ、変わったら再生成

迷ったら手続き側に倒す ― AIが安く再生成できるので、必要になってから定義へ昇格すればよい。

24 アンチパターン

現場で踏む地雷

!

定義のドリフト / 二重ソース

型・スキーマ・ドキュメントがズレていく。対策: 単一ソースから生成する

!

ブラックボックスDSL

AI製エンジンを誰も読めない。対策: 解釈器は小さく・人が読める範囲に

!

テストなき自己修正ループ

AIが“通る”までコードを壊す。対策: 契約テストを先に置く

!

手作業での介入

生成コードに手を入れ再生成不能に。対策: 直すのは常に定義側

共通の処方箋はひとつ ― 「単一の定義から、決定的に導く」 を崩さないこと。
