01 あるある

仕様が変わるたび、if が増えていく

「条件をひとつ足すだけ」のはずが、毎回 分岐の組合せ・順序・抜け漏れ に悩む。テストも一緒に壊れる。
機能追加のコストが、機能の数に比例せず指数的に膨らんでいく。なぜだろう？

function handle(req) { if (req.type === "A") { /* ... */ } else if (req.type === "B") { /* ... */ } else if (req.type === "C") { /* ... */ } else if (req.type === "D") { /* ← 今日もまた一行 */ } // ...そして誰も全体を読めなくなる }
02 問い

そもそも「仕様」は何で書かれている？

How — 手順

手続き

「まず◯◯して、次に△△、もし□□なら…」
= 計算をどう実行するかの連なり。

What — 定義

定義

「正しい入力とは / 価格とは / 状態とは」
= 対象が何であるかの取り決め。

仕様書はたいてい 定義（What） で書かれている。なのに私たちはコードを 手続き（How） で書きがち。このズレこそが、変更を難しくしている正体。

03 言葉の整理

手続き的 と 定義的

手続き的

計算の手順をコードに直接書く。ループ・分岐・代入の連なり。
知識がコード（制御フロー）の中に溶けている。

定義的

対象をデータ・型・スキーマ・表として宣言し、それを解釈する汎用の仕組みを1つ用意する。
知識がデータとして外に出ている。

定義をデータとして表し、それを解釈する仕組みを用意する — これが データ駆動 / 宣言的プログラミング の核。SQL・正規表現・CSS・React も同じ系譜にある。

04 なぜ強いのか

変更の局所性

Δ仕様≈Δコード

コードの構造を 「定義」の構造 に合わせると、
仕様の 1つの変更 が、コードの 1つの箇所 に対応する。

保守性の正体は、変更が一箇所に収まるか。

手続きに定義を埋め込むと、1つの定義変更が手順のあちこちに散る（非局所）。これが指数的コストの原因。

05 例1 · FizzBuzz

まずは手続き版

手続き · imperative
function fizzbuzz(n) { for (let i = 1; i <= n; i++) { if (i % 15 === 0) print("FizzBuzz"); else if (i % 3 === 0) print("Fizz"); else if (i % 5 === 0) print("Buzz"); else print(i); } }

3→Fizz、5→Buzz、両方→FizzBuzz。いまは 4分岐。ここに仕様追加「7の倍数 → Bazz」が来たら、どうなる？

05 例1 · 仕様追加: 7の倍数 → "Bazz"

同じ変更、ぜんぜん違う影響

手続き
if (i % 105===0) print("FizzBuzzBazz"); else if (i % 21 ===0) print("FizzBazz"); else if (i % 35 ===0) print("BuzzBazz"); else if (i % 15 ===0) print("FizzBuzz"); else if (i % 7 ===0) print("Bazz"); else if (i % 3 ===0) print("Fizz"); else if (i % 5 ===0) print("Buzz"); else print(i);
分岐が 4 → 8 に倍増。組合せ（21, 35, 105…）を手で網羅し、順序も正しく並べ替える必要がある。
変更 = 分岐の作り直し / 抜け漏れ注意
定義
const rules = [ { divisor: 3, word: "Fizz" }, { divisor: 5, word: "Buzz" }, { divisor: 7, word: "Bazz" }, ]; // 解釈する仕組みは一切触らない // 21="FizzBazz" 等の組合せは自動
「Fizz とは何か」を定義しているので、組合せは定義から自動で導かれる。手続き本体には手を入れない。
変更 = データに +1 行

参考 · 定義版の本体： rules.filter(r => i % r.divisor === 0).map(r => r.word).join("") || i

06 例2 · 入力バリデーション

ルールを「スキーマ」として定義する

手続き
function validate(form) { if (!form.email) return "メール必須"; if (!isEmail(form.email)) return "メール形式が不正"; if (form.age == null) return "年齢必須"; if (form.age < 0) return "0以上で"; // 項目が増えるたび関数が伸びる… }
検証ルールが手続きの中に散在。項目追加・順序・国際化で関数が肥大化する。
定義
const schema = { email: [required(), pattern(EMAIL)], age: [required(), min(0), max(150)], name: [required(), maxLen(40)], }; // 汎用バリデータが schema を解釈 const errors = validate(form, schema);
仕様 = スキーマ。項目やルールの増減はデータ編集で済む。Zod / JSON Schema はこの発想の製品化。

おまけ — スキーマはそのままフォーム生成・APIドキュメント・型にも使い回せる。定義が単一の真実の源になる。

07 例3 · 状態遷移

遷移を「表」として定義する

手続き
if (order.isPaid && !order.isShipped && !order.isCanceled) { order.isShipped = true; } // boolフラグの組合せで // "未払いなのに発送済" も表現できてしまう
状態がフラグの組合せに散る。ありえない状態が型上は作れてしまう。
定義
type State = "draft"|"paid"|"shipped"|"done"; const next = { draft: { pay: "paid" }, paid: { ship: "shipped" }, shipped: { deliver: "done" }, shipped2:{ returnReq: "returning" }, } as const;
状態と遷移を表に定義。状態追加 = 表に1行。型に無い状態は表現不可能（make illegal states unrepresentable）。

遷移の実行はすべて next[state][event] という1つの汎用関数に集約される。

08 例4 · 料金・割引

ビジネスルールをデータにする

定義 · rules as data
const rules = [ { when: c => c.total >= 5000, off: 500, label: "5千円以上" }, { when: c => c.has("SPRING"), off: 0.10, label: "春クーポン" }, { when: c => c.isMember, off: 0.05, label: "会員割" }, ]; const applied = rules.filter(r => r.when(cart));

新キャンペーン = 配列に1要素追加。割引の「定義」とコードが1対1に対応する。企画書の表をそのままコードに写せる状態が理想。

09 原則

「定義を実装する」ための道具箱

A

データ駆動 / 表駆動

知識をコードでなくデータに置き、解釈する汎用の仕組みを1つ用意する。

B

宣言的に書く

How でなく What を記述。SQL・正規表現・CSS の発想を自分のコードにも。

C

語彙を仕様に合わせる

仕様書の名詞・動詞が、同じ名前でコードに現れる。仕様の一文が探せる。

D

型で定義を表す

直和型などで不正な状態を表現不可能に。違反はコンパイルエラーへ。

E

単一の真実の源 (SSOT)

定義は一箇所だけに置く。コピーされた定義は必ずズレる。

10 注意

「定義化」はいつでも正解、ではない

!

過剰抽象 (YAGNI)

2個しかなく今後も変わらない分岐に、汎用エンジンはやりすぎ。素直な if が読みやすい。

!

間違った抽象は無抽象より悪い

ドメインに合わない「定義」は、将来ずっと足かせになる。安易に共通化しない。

!

3度の法則

同じ形の分岐が3回現れたら、データに切り出す目安。早すぎる抽象化は避ける。

!

可読性・デバッグ性

間接化はステップ実行を追いにくくする。読み手のコストとのトレードオフを意識。

変わる軸にだけ「定義」を。変わらない所は素直な手続きで。
11 見抜き方

レビューで使えるチェックリスト

  • 仕様書の一文が、コードの一箇所に対応しているか？
  • 仕様追加のたびに if/else が増えるなら、定義がコードに埋もれているサイン
  • 同じ形の分岐が 3回 出たら、データに切り出せないか検討
  • ありえない状態を、型やデータの形で弾けているか
  • 同じ定義が複数箇所にコピーされていないか（SSOT）
12 まとめ
手続きは「いま」を解く。
定義は「仕様」を解く。

コードを仕様の写像にすれば、
仕様変更は写像のまま、小さく一箇所に収まる。

13 前提

第1部の論拠は「人間の保守性」だった

変更の局所性も、不正な状態の排除も、根拠は結局 「人間が読み・直し・壊さない」 ため。
では、コードの多くを AIが書く なら、この話は変わるのか？

優劣というより —— AI駆動開発は 定義型を相対的に有利にする。ただし理由が変わり、油断すると逆に手続きが増殖する。
14 核心

ボトルネックが移動する

人間が手で書く時代
書く
直す
AIに任せる時代
書く
意図を伝える
出力を検証する

「書く」コストは縮み、重心は 意図を伝える と 出力を検証する へ移る。そして —— このどちらも、定義型に味方する。

15 含意 ①

定義型が効く、二つの局面

Tell — 伝える

宣言 = 仕様 = 良い指示

型・スキーマ・ルール表は、そのまま仕様であり、そのままAIへの曖昧さの少ない指示になる。手続きを言葉で説明するより、定義を渡す方が速く正確。

const schema = { age: [min(0), max(150)] }
Verify — 検証する

目視で照合できる

ルール表は仕様書と突き合わせて確認できる。手続きは実行を追わないと正しさを判断できない。AIへの委譲が増えるほど、この「検証の安さ」が効いてくる。

人間時代の論拠は「直しやすさ」。AI時代の論拠は 「伝えやすさ」と「確かめやすさ」 に移る。

16 含意 ②

機械可読な定義は、AIの自己修正ループになる

定義
型・テスト・網羅された状態
生成›
AIが実装
手続きを書く
検査›
型エラー / 失敗
違反が機械的に弾かれる
修正›
AIが直す
自分で再試行
↻ パスするまで、人手を介さず反復できる

「不正な状態を表現不可能に」しておくほど、AIの間違いはコンパイルエラーで止まる。ガードレールが厚いほど、エージェントは自律的に走れる。緩い手続き型は、この信号が乏しい。

17 含意 ③ · 第1部の「あるある」再び

AIは「もう1つ if を足す」を、最もやりがち

手続き
if (t === "A") handleA(req); else if (t === "B") handleB(req); else if (t === "C") handleC(req); else if (t === "D") handleD(req); // AIがまた継ぎ足す
エージェントはターンごとに局所的なプロンプトで動く。全体を見て定義へ寄せるより、目の前に分岐を足す。
第1部の失敗を高速に再生産
定義
const handlers = { A: handleA, B: handleB, C: handleC, D: handleD, }; handlers[t]?.(req);
定義中心の構造なら、同じプロンプトでもAIの手は「データに1行」へ向かう。アーキテクチャがAIのお行儀を決める。
変更 = データに +1 行

だからこそ「定義に寄せる設計」は、AI時代にこそ効く。良い構造は、AIを良い変更へと誘導する“レール”になる。

18 反対側

ただし、過剰抽象の罠は増幅する

!

一瞬でDSLが作れる

AIはルールエンジンやDSLを即生成できる。誰も理解していない仕組みが生まれやすい。

!

解釈器がブラックボックス化

定義もエンジンもAI製だと中身が不透明。平たい手続きの方が監査しやすいこともある。

!

「間違った抽象」がより重い

第1部の警句 —— 間違った抽象は無抽象より悪い —— がAI時代に重みを増す。

!

修正コストも下がった

「直すのが面倒」という抽象化の動機の一部は、AIが消してしまった。

安く作れることは、作るべき理由にはならない。
19 結論

問いは「優劣」ではなく「境界」

手続き（How）AIが生成する · 再生成可能 · “使い捨て”の実装
定義（What）人間が所有・レビューする · 機械検査可能 · “耐久資産”
型スキーマルール表状態遷移表

仕様が変わったら —— 定義を直し、手続きはAIに書き直させる。守るべき中核と、捨てられる外側を分けておく。これがAI時代の設計の重心。

20 落とし穴

最小抵抗経路は「とりあえず手続きを生成」

AIに頼むと、まず手続きが出てくる。書くコスト（即時）は消えるが、検証・ドリフト・局所性のコスト（遅延）は見えにくい。放っておけば、コードは手続きへと回帰していく。

だから「定義に寄せる規律」は、人間が手で書いていた時代より、いっそう意識的に持つ必要がある。
21 収束

仕様駆動・意図駆動 は、定義型設計の別名

近年のAI開発スタイル —— 仕様を書き、AIが実装する —— は、第1部の「定義を実装する」とほぼ同じ方向を向いている。

仕様こそが、プログラム。

宣言的設計とAI駆動開発は、別々の動機から生まれて、同じ場所に着いた。

22 まとめ
AIが 手続き を安く書けるからこそ、
人間が握るべき資産は 定義 に寄る。

手続きの優劣ではない。何を「定義」として耐久資産に持ち、
何を「手続き」としてAIに再生成させ捨てるか —— その線引きが本質。

23 方針

「やる」と決めたら、問いは How に変わる

第1部は原則（なぜ定義か）、第2部はAI時代の含意（むしろ有利、ただし罠）。
AI駆動開発で進めると決まったいま、必要なのは 「どう回すか」 の具体です。

第3部は ― 定義ファーストのAI駆動開発を、現場で回すためのプレイブック。
24 全体像

三者で分業する

Human 定義 仕様・型・ルールを書き、所有し、レビューする。意図と一致しているかを保証する唯一の役。
AI 手続き 定義から手続きを生成・改修する。出力は再生成可能な“使い捨て”として扱う。
Machine 検査 型・テスト・CIが定義への違反を機械的に弾く。AIの自己修正ループを支える土台。

この分業が崩れる瞬間に問題が起きる ― 人が手続きに手を入れて再生成不能にする、定義をAIに丸投げする、検査が無いまま生成を信じる。役割の境界を守ることが運用の核。

25 定義の置き場

定義はどこに宿すか

仕様ドキュメント / ADR自然言語の定義。AIへの一次入力人が所有
リポジトリ規約CLAUDE.md 等。AIへの恒常的なルール人が所有
スキーマ型・実行時検証・ドキュメントを一枚で兼ねる常時検査
状態遷移表 / ルール表データとしての定義常時検査
テスト実行可能な仕様＝契約常時検査
型最も安く、常に効く定義常時検査

上ほど人が所有する自然言語、下ほど機械が常時検査する形式。機械検査可能な層に寄せるほど、AIの自己修正が効く。最上流の自然言語の定義は、形式の層とズレないよう一本化しておく。

26 ワークフロー

1サイクルの回し方

定義を更新
人が仕様・型・表を書く
生成›
AIが実装
手続きを生成・改修
検査›
機械が検査
型・テスト・CI／失敗は自己修正へ
確認›
人がレビュー
見るのは「定義の差分」
↻ 検査が通るまではAIが自律的に反復 ― 人手が入るのは両端（定義とレビュー）だけ

コードレビューの重心が 「手続きの差分」から「定義の差分」へ 移る。手続きの正しさは機械が保証し、人は意図との一致だけを見る。

27 初期投資

ガードレールは「先に」作る

A

厳しい型

any禁止・網羅性チェック。不正な状態を表現不可能にし、AIの間違いをコンパイルで止める。

B

契約としてのテスト

出力値でなく不変条件を縛る（プロパティ/契約テスト）。「通った」が「正しい」になる。

C

CIを自己修正ループに

型・テスト・lintをAIが回せる速さで自動実行。失敗が即フィードバックになる。

D

具体的な失敗メッセージ

失敗が機械可読で具体的なほど、AIは自分で直せる。曖昧な失敗は人を呼び戻す。

第2部の「ガードレールが厚いほどAIは自律的に走れる」を、具体に落とした回。薄いガードレールの下では、AIは静かに間違える。

28 レビュー

人が見る場所が変わる

  • 見ているのは 「定義の差分」 か？手続きの差分は機械任せでよい
  • その手続きは、定義から決定的に導けるか？導けないなら、定義が不足しているサイン
  • 定義は 意図と一致 しているか？ここだけは、最後まで人間の仕事
  • 生成コードに 手で継ぎ足していない か？再生成可能性を壊さない
  • その抽象は 「3度」現れた実需 に基づくか？AI製DSLの過剰を弾く
29 境界の引き方

何を定義にし、何を手続きに捨てるか

定義にする

  • それが仕様変更の「軸」そのものである
  • 同じ形の分岐が3度現れた
  • 仕様書に表として書ける構造をしている

手続きでよい

  • いま2個で、今後も変わらない分岐
  • その分岐は仕様の軸ではない
  • 解釈器を作るほうが高くつく（YAGNI）

AIは“安いから作れてしまう”。だから境界は YAGNI 寄りに引く。変わる軸にだけ定義を置き、変わらない所は素直な手続きでAIに再生成させる。
