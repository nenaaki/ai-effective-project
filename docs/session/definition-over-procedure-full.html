01 あるある

仕様が変わるたび、if が増えていく

「条件を1つ足すだけ」のはずが、毎回 分岐の組合せ・順序・抜け漏れ に悩む。テストも一緒に壊れる。機能追加のコストが、機能数に比例せず 指数的に膨らむ ― なぜ？

function handle(req) { if (req.type === "A") { /* ... */ } else if (req.type === "B") { /* ... */ } else if (req.type === "C") { /* ... */ } else if (req.type === "D") { /* ← 今日もまた一行 */ } // ...そして誰も全体を読めなくなる }

1本足す・順序を変えるだけで 後続の分岐すべての挙動が変わりうる。影響がその行に閉じないのが厄介。

02 問い

仕様は「定義」で書かれている

How — 手順

手続き

「まず◯◯、次に△△、もし□□なら…」
＝計算をどう実行するか。知識が制御フローに溶ける。

What — 定義

定義

「正しい入力とは／価格とは／状態とは」
＝対象が何であるか。知識がデータとして外に出る。

仕様書は 定義（What） で書かれるのに、コードは 手続き（How） で書きがち。このズレが変更を難しくする。定義をデータで表し、解釈する汎用の仕組みを1つ用意する ― これが 宣言的プログラミング（SQL・正規表現・CSS・React）の核。

03 なぜ強いのか

変更の局所性

Δ仕様≈Δコード

コードの構造を 「定義」の構造 に合わせると、
仕様の 1つの変更 が、コードの 1箇所 に対応する。

保守性の正体は、仕様の1変更がコードの1箇所に収まるか。

逆に手続きへ定義を埋め込むと、仕様を1つ変えただけでも 影響が1箇所に収まらず、手順のあちこちに波及する。これが指数的コストの原因。

04 例1 · FizzBuzz — 仕様追加: 7の倍数 → "Bazz"

同じ変更、ぜんぜん違う影響

手続き
if (i % 105===0) print("FizzBuzzBazz"); else if (i % 21 ===0) print("FizzBazz"); else if (i % 35 ===0) print("BuzzBazz"); else if (i % 15 ===0) print("FizzBuzz"); else if (i % 7 ===0) print("Bazz"); else if (i % 3 ===0) print("Fizz"); else if (i % 5 ===0) print("Buzz"); else print(i);
分岐が 4 → 8 に倍増。組合せ（21, 35, 105…）を手で網羅し、順序も並べ替える必要がある。
変更 = 分岐の作り直し / 抜け漏れ注意
定義
const rules = [ { divisor: 3, word: "Fizz" }, { divisor: 5, word: "Buzz" }, { divisor: 7, word: "Bazz" }, ]; // ↓ この定義を動かす本体（変更不要） const out = rules .filter(r => i % r.divisor === 0) .map(r => r.word).join("") || i;
「Fizz とは何か」を定義するので、組合せは定義から自動で導かれる。本体には手を入れない。
変更 = データに +1 行

定義（データ）と解釈する1つの汎用ロジックを分離 ― 仕様追加はデータに1行、ロジックは不変（21=FizzBazz 等の組合せも自動）。

05 例2 · 入力バリデーション

ルールを「スキーマ」として定義する

手続き
function validate(form) { if (!form.email) return "メール必須"; if (!isEmail(form.email)) return "メール形式が不正"; if (form.age == null) return "年齢必須"; if (form.age < 0) return "0以上で"; // 項目が増えるたび関数が伸びる… }
検証ルールが手続きに散在。項目追加・順序・国際化で関数が肥大化する。
定義
const schema = { email: [required(), pattern(EMAIL)], age: [required(), min(0), max(150)], name: [required(), maxLen(40)], }; // 汎用バリデータが schema を解釈 const errors = validate(form, schema);
仕様 = スキーマ。項目やルールの増減はデータ編集で済む。Zod / JSON Schema はこの発想の製品化。

スキーマはそのままフォーム生成・APIドキュメント・型にも使い回せる。定義が単一の真実の源になる。

06 例3 · 状態遷移

同じ「マトリクス」を、手続き と 定義 で表す

マトリクス＋型 · 仕様
state＼eventpaycancelshipdeliverreturnReq
draftpaidcanceled···
paid·canceledshipped··
shipped···done·
done····returned
returned·····
canceled·····
// 表を型で固定（中央・右で共用） type State = "draft"|"paid"|"shipped" |"done"|"returned"|"canceled"; type Event = "pay"|"cancel"|"ship" |"deliver"|"returnReq"; type Table = Partial<Record<State, Partial<Record<Event, State>>>>;
行＝状態、列＝イベント、セル＝次の状態。表と型が唯一の仕様 ― 中央・右はこれを写す。
手続き · imperative
function next(s: State, e: Event): State { if (s==="draft" && e==="pay") return "paid"; if (s==="draft" && e==="cancel") return "canceled"; if (s==="paid" && e==="ship") return "shipped"; if (s==="paid" && e==="cancel") return "canceled"; if (s==="shipped" && e==="deliver") return "done"; if (s==="done" && e==="returnReq") return "returned"; return s; // それ以外は現状維持 }
セル1つ = 分岐1本。状態×イベントの数だけ if が増える。順序・抜け漏れも人手で管理する。
定義 · declarative
const table: Table = { draft: { pay: "paid", cancel: "canceled" }, paid: { ship: "shipped", cancel: "canceled" }, shipped: { deliver: "done" }, done: { returnReq: "returned" }, }; function next(s: State, e: Event): State { return table[s]?.[e] ?? s; // 表を引くだけ }
型付きの表そのもの。遷移追加 = 行/列に1要素。表に無い状態・イベントはコンパイルエラー。

同じマトリクス（左）を手続き（中）と定義（右）で表現。State/Event を型で固定したので両方とも引数・戻り値が型安全。手続きはセルの数だけ分岐が要り、定義は表を写すだけ ― 表に無い状態・イベントはコンパイルで弾ける。

07 原則と注意

定義に寄せる ― 道具と、引き際

使う：定義に寄せる道具

  • データ / 表駆動 ― 知識をデータに出し、解釈する汎用の仕組みを1つ
  • 宣言的に ― How でなく What（SQL・正規表現・CSS の発想）
  • 仕様の語彙に合わせる ― 仕様の一文がコードで探せる
  • 型で表す ― 不正な状態を表現不可能に（違反はコンパイルエラー）
  • SSOT（単一の真実の源）― 定義は一箇所だけに置く。コピーは必ずズレる

引く：やりすぎない

  • 過剰抽象 (YAGNI) ― 「たぶん要らない（You Aren't Gonna Need It）」。2個で不変の分岐に汎用エンジンは過剰
  • 間違った抽象は無抽象より悪い ― 合わない定義は将来の足かせ
  • 3度の法則 ― 同じ形が3回現れてからデータに切り出す
  • 可読性・デバッグ性 ― 間接化は追いにくさとのトレードオフ
変わる軸にだけ「定義」を。変わらない所は素直な手続きで。
08 見抜き方

レビューで使えるチェックリスト

  • 仕様書の一文が、コードの一箇所に対応しているか？
  • 仕様追加のたびに if/else が増えるなら、定義がコードに埋もれているサイン
  • 同じ形の分岐が 3回 出たら、データに切り出せないか検討
  • ありえない状態を、型やデータの形で弾けているか
  • 同じ定義が複数箇所にコピーされていないか（SSOT）
09 まとめ
手続きは「いま」を解く。
定義は「仕様」を解く。

コードを仕様の写像にすれば、
仕様変更は写像のまま、小さく一箇所に収まる。

10 前提

第1部の論拠は「人間の保守性」だった

変更の局所性も、不正な状態の排除も、根拠は 「人間が読み・直し・壊さない」 ため。では、コードの多くを AIが書く なら、この話は変わるのか？

AI駆動開発は 定義型を相対的に有利にする。ただし理由が変わり、油断すると逆に手続きが増殖する。
11 核心

ボトルネックが移動する

人間が手で書く時代
書く
直す
AIに任せる時代
書く
意図を伝える
出力を検証する

「書く」コストは縮み、重心は 意図を伝える と 出力を検証する へ移る。そして、このどちらも 定義型に味方する。

12 含意 ①

定義型が効く、二つの局面

Tell — 伝える

宣言 = 仕様 = 良い指示

型・スキーマ・ルール表は、そのまま仕様であり、AIへの曖昧さの少ない指示になる。手続きを言葉で説明するより速く正確。

const schema = { age: [min(0), max(150)] }
Verify — 検証する

目視で照合できる

ルール表は仕様書と突き合わせて確認できる。手続きは実行を追わないと正しさを判断できない。委譲が増えるほど「検証の安さ」が効く。

人間時代の論拠は「直しやすさ」。AI時代の論拠は 「伝えやすさ」と「確かめやすさ」 に移る。

13 含意 ②

機械可読な定義は、AIの自己修正ループになる

定義
型・テスト・網羅された状態
生成›
AIが実装
手続きを書く
検査›
型エラー / 失敗
違反が機械的に弾かれる
修正›
AIが直す
自分で再試行
↻ パスするまで、人手を介さず反復できる

「不正な状態を表現不可能に」しておくほど、AIの間違いはコンパイルエラーで止まる。ガードレールが厚いほど、エージェントは自律的に走れる。緩い手続き型は、この信号が乏しい。

14 含意 ③ · 第1部の「あるある」再び

AIは「もう1つ if を足す」を、最もやりがち

手続き
if (t === "A") handleA(req); else if (t === "B") handleB(req); else if (t === "C") handleC(req); else if (t === "D") handleD(req); // AIがまた継ぎ足す
エージェントはターンごとに局所的なプロンプトで動く。全体を見て定義へ寄せるより、目の前に分岐を足す。
第1部の失敗を高速に再生産
定義
const handlers = { A: handleA, B: handleB, C: handleC, D: handleD, }; handlers[t]?.(req);
定義中心の構造なら、同じプロンプトでもAIの手は「データに1行」へ向かう。アーキテクチャがAIのお行儀を決める。
変更 = データに +1 行

そもそもAIは周囲の既存コードのスタイルに倣う ― 手続き的なコードには手続きを、定義的なコードには定義を足す。だから「定義に寄せる設計」はAI時代にこそ効く。良い構造が、AIを良い変更へ誘導する“レール”になる。

15 反対側

ただし、過剰抽象の罠は増幅する

!

AI製DSLがブラックボックス化

AIはDSL/ルールエンジンを即生成できるが、定義もエンジンもAI製だと誰も中身を読めない。平たい手続きの方が監査しやすいことも。
※ DSL＝独自のルール記法＋解釈器（例: SQL・正規表現）

!

「間違った抽象」がより重い

間違った抽象は無抽象より悪い ― 第1部の警句がAI時代に重みを増す。

!

修正コストも下がった

「直すのが面倒」という抽象化の動機の一部を、AIが消してしまった。

安く作れることと作る価値があることは別 ― 抽象は「安いから」ではなく「必要だから」作る。
16 結論

問いは「優劣」ではなく「境界」

手続き（How）AIが生成する · 再生成可能 · “使い捨て”の実装
定義（What）人間が所有・レビューする · 機械検査可能 · “耐久資産”
型スキーマルール表状態遷移表

仕様が変わったら ― 定義を直し、手続きはAIに書き直させる。守るべき中核と捨てられる外側を分ける。これがAI時代の設計の重心。最小抵抗経路は「とりあえず手続きを生成」なので、定義に寄せる規律は、人間時代よりいっそう意識的に持つ。

17 まとめ
AIが 手続き を安く書けるからこそ、
人間が握るべき資産は 定義 に寄る。

何を「定義」として耐久資産に持ち、
何を「手続き」としてAIに再生成させ捨てるか ― その線引きが本質。

仕様こそが、プログラム。

18 お題 · これを作る

CSVを読み込んで、検証する

入力 · CSV（1行目＝カラム名）
名前,年齢,住所 山田太郎,34,東京都新宿区… 佐藤花子,29,大阪府大阪市… 鈴木一郎,-5,
列の順番も、不正値（-5）や空欄も、現実には混ざる。
仕様 · 人間の言葉（定義の源）
# 取り込む列 → フィールド / 型 / 検証 名前 → name string / 必須 / 最大40 年齢 → age number / 必須 / 0〜120 住所 → address string / 必須 # 不正な行はまとめてエラーで返す
人が所有する仕様。これを実装に落としていく。

やることは3つ ― ① 列をフィールドへ対応・② 型変換・③ 検証。これをAIにどう頼むかで、出てくるコードが変わる。

19 分かれ道 · 同じ仕様、違う頼み方

同じAIでも、頼み方で出力が変わる

指示A · やりたいことだけ伝える
「CSVを読み込んで。1行目がカラム名。名前・年齢・住所を name / age / address に取り出して、数値に変換、必須チェックと年齢0〜120の検証もして。」
手順の言葉で頼む → AIは最短で1本の関数に分岐と throw を並べる。
→ 手続きコード（次ページ）
指示B · 成果物の「形」を指定する
「手続き的に書かないで。① 列対応・型変換・検証を定義テーブル schema にする ② schema を読む汎用クラス CsvMapper を1つ書く（分岐を書かない）③ 出力型は schema から導出、エラーは集約。仕様は添付の仕様書のとおり。」📎 仕様書を添付
構造と禁止事項を指定 → 定義と汎用エンジンに分離する。
→ 定義ファースト（この先）

仕様の中身はまったく同じ。違うのは「手順を述べたか、定義と構造を述べたか」だけ。定義ファーストは、まず“指示の側”で定義に寄せること ― AIは放っておくと手続きに倒れる。

20 指示A の結果 · 第1部の再来

手続きだと、対応・型変換・検証が絡まる

手続き
// CSVを1行ずつ、手で組み立てる for (let i = 1; i < lines.length; i++) { const c = lines[i].split(","); const name = c[0]; // ① 列の位置を直書き const age = Number(c[1]); // ② 型変換も手書き const address = c[2]; if (!name) throw "名前必須"; // ③ 検証が散らばる if (name.length > 40) throw "名前長すぎ"; if (isNaN(age)) throw "年齢が数値でない"; if (age < 0 || age > 120) throw "範囲外"; if (!address) throw "住所必須"; out.push({ name, age, address }); }
①対応・②型変換・③検証が1つの手順に溶けている。列の追加・順序変更も、ここを書き換える。
列を1つ足す = この手順を数行書き換え

第1部の「if が増える」が CSV でも再来。しかも throw は最初の1件で止まり、全エラーを返せない ― 3つの関心事を分離しよう。

21 STEP ① · 定義（指示B）

仕様を、そのままテーブルに写す

定義 · フィールド定義テーブル
// 列→フィールド・型変換・検証を 1 つの表に const schema = { name: { col: "名前", as: str, rules: [required(), maxLen(40)] }, age: { col: "年齢", as: num, rules: [required(), min(0), max(120)] }, address: { col: "住所", as: str, rules: [required()] }, };
col＝CSVの列名、as＝型変換、rules＝検証。仕様の一行が、表の一行に対応する。
部品 · 小さく再利用
// 型変換（raw文字列 → 値） const str = (s) => s.trim(); const num = (s) => Number(s); // 検証ルール（第1部と同じ語彙） const required = () => ({ ok: v => v !== "" && v != null, msg: "必須" }); const min = (n) => ({ ok: v => v >= n, msg: n + "以上" }); const max = (n) => ({ ok: v => v <= n, msg: n + "以下" });
変換も検証も小さな部品。表から名前で呼ぶだけ。

これが定義ファースト ― 「何を」（What）だけを宣言し、「どう」（How）は書かない。第1部のスキーマと同じ形。

22 STEP ② · 汎用エンジン

定義を解釈する、1つの汎用クラス

型 · 定義から自動で決まる
type Conv<T> = (raw: string) => T; type Rule<T> = { ok: (v: T) => boolean; msg: string }; type Field<T> = { col: string; as: Conv<T>; rules: Rule<T>[] }; type Schema = Record<string, Field<any>>; // 出力の型を定義から導出（手で書かない） type Row<S> = { [K in keyof S]: S[K] extends Field<infer T> ? T : never };
汎用 · CsvMapper（変更不要）
class CsvMapper<S extends Schema> { constructor(private schema: S) {} parse(csv: string) { const [head, ...lines] = csv.trim().split("\n"); const cols = head.split(","); const rows: Row<S>[] = [], errors = []; lines.forEach((line, i) => { const cells = line.split(","); const rec = {}; for (const key in this.schema) { const f = this.schema[key]; const raw = cells[cols.indexOf(f.col)] ?? ""; const v = f.as(raw); // ② 型変換 for (const r of f.rules) // ③ 検証 if (!r.ok(v)) errors.push( { line: i+2, field: key, msg: r.msg }); rec[key] = v; // ① 対応 } rows.push(rec as Row<S>); }); return { rows, errors }; } }

①対応・②型変換・③検証を、定義から決定的に実行する。このエンジンは仕様が変わっても触らない ― 変わるのは schema だけ。

23 STEP ③ · 実行

流すだけ ― 型付きの結果と、エラー集約

使う
const { rows, errors } = new CsvMapper(schema).parse(csv); // rows は型推論される ↓ // { name: string; age: number; address: string }[] rows[0].age + 1; // ✅ number として扱える
戻り値の型は Row<S> でschema から自動導出。age は number、キャスト不要。
エラー · まとめて返る
errors = [ { line: 4, field: "age", msg: "0以上" }, { line: 4, field: "address", msg: "必須" }, ]
throw で止めず、全行・全項目を集約。どこが悪いか一覧で分かる。

人が書いたのは schema（定義）だけ。列の対応・型変換・検証・エラー集約は、汎用エンジンが定義から導いた。

24 仕様変更 · 第1部の答え合わせ

「メール」列が増えた ― さて、何行直す？

定義 · テーブルに1行
const schema = { name: { col: "名前", as: str, rules: [required(), maxLen(40)] }, age: { col: "年齢", as: num, rules: [required(), min(0), max(120)] }, address: { col: "住所", as: str, rules: [required()] }, email: { col: "メール", as: str, rules: [required(), pattern(EMAIL)] }, };
変更 = データに +1 行
波及 · ぜんぶ自動
// 出力の型も自動で増える type Row = { name: string; age: number; address: string; email: string; // ← 追加 } // CsvMapper は 1 文字も変更不要
列の対応・型変換・検証・型定義 ― すべて schema 一箇所から。Δ仕様 ≈ Δコード。

第1部の「1行足すだけ」が、実物でも本当に1行。変更が定義の一箇所に閉じる ― これが目指した形。

25 分担 · これがAI駆動開発

誰が、何を書いたか

人間 — 所有する 定義 仕様と schema（テーブル）。意図そのもの。ここだけは手放さない。
AI — 生成する エンジン CsvMapper・型変換・検証部品。定義が固まれば、いつでも書き直せる使い捨て。
機械 — 検査する 型・テスト Row<S> の型・エラー集約・テストが、定義どおりかを自動で弾く。

変わるのはテーブルだけ。人がそこを握り、AIがエンジンを生成し、機械が検査する ― 第2部の分担が、そのまま実物に落ちている。
