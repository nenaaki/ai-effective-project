「仕様をひとつ足す」だけで、こんなに差が出る

ボタンを押して、仕様（例：「7の倍数なら Bazz」）を追加してみてください。手続き的なコードと定義的なコードで、1回の変更の“重さ”がどう変わるか。

追加した仕様 0 個
手続き · if / else
3分岐を作り直し
条件が増えるたび、組合せ（2ⁿ−1）と順序を手で網羅しなおす。変更が全体に散る。
定義 · rules as data
+1行 追加するだけ
ルールを定義しているので、組合せは自動で導かれる。変更は一箇所に収まる。
1回の仕様追加で“触るコード量”（相対）
手続き3 分岐
定義+1 行

これは第1部で扱う 「変更の局所性（Δ仕様 ≈ Δコード）」 の実演です。勉強会では、この考え方を実務のコードへ落とし込みます。

こんな経験、ありませんか？

「条件を1つ足すだけ」のはずが、分岐が爆発した
仕様変更のたびに、テストが一緒に壊れる
どこを直せば全部直るのか、誰も分からない
AIに任せたら、手続きが増殖していった

原因の多くは、「定義」がコードに埋もれていること。この勉強会では、その見抜き方と直し方を、手を動かしながら学びます。
