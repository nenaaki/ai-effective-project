FOR PM / PO — SCOPE & QUALITY ASSURANCE

仕様変更のデグレード範囲を
「予測可能」にするAIエージェント

regression-scope は、仕様変更を反映した後に「どの画面・操作をテストすべきか」を、 仕様書と実装差分の両面から特定して文書化します。 PM/PO にとっては、テストスコープの確定・要件トレーサビリティ・リリース判断の参考情報を 属人化させずに手に入れやすくする仕組みです。

テストスコープの自動確定 要件↔実装の整合チェック テスト工数の初期見立て 過去知見の学習・蓄積 リリース判断の参考情報

開発フローのどこで動くか

regression-scope は運用上2つのタイミングで動く。AIによる実装完了後の「範囲確定」と、人間が目視確認・微調整した後の「PR作成時の再確認」である。

要件・仕様策定 → AI実装 / レビュー合格 → ★ regression-scope（範囲確定） → 👤 人間が目視＋AIで微調整 → ★ regression-scope（PR時に再確認） → テスト実施 → リリース判断

1回目（範囲確定）：全実装が完了した後（フロントエンドの最終レビュー合格後）に、開発フローの最終ステップとして自動起動する。1回の起動内で3段階の調査を行う。
　① 範囲推定：仕様書から「変わるはず」の影響範囲を先読みする。
　② 差分確認：実装差分（PRの変更）と照らし合わせ、推定が実装に反映されているか確認する。
　③ 乖離分析：推定とのズレ（やり残し・想定外の変更）を検出し、テスト範囲を確定する。
人間による目視＋AI微調整：確定した範囲・実装を人間がレビューしながら、必要な手直しをAIに指示して仕上げる（Human-in-the-loop）。
2回目（PR作成時の再確認）：微調整で変わった内容を踏まえ、PR作成のタイミングで regression-scope にテスト観点を再確認させ、スコープを最新の実装に追従させる。

主要な観点での AsIs → ToBe

① テストスコープの確定
AsIs
  • 「どこまでテストするか」は開発者の口頭報告ベース。粒度が案件・人で揺れる。
  • スコープの根拠が曖昧で、PM/PO が妥当性を判断しづらい。
  • 影響画面の数え漏れが、テスト計画の抜けに直結。
ToBe
  • 影響する画面・API・操作が一覧化され、根拠（どの変更が波及したか）付きで提示される。
  • 「スコープ外」とその理由も明記され、線引きを PM/PO が確認できる。
  • 画面ごとの確認手順まで生成され、そのままテスト計画の素材になる。
② 要件トレーサビリティ（仕様↔実装）
AsIs
  • 仕様どおり作られたか、余計な変更が無いかは、レビューで人が気づくかどうか。
  • 「仕様にあるのに未実装」「仕様外の変更」が後工程まで見過ごされやすい。
ToBe
  • 仕様書の「変わるはず」と実装の「実際に変わった」を突き合わせて差分を提示。
  • 実装漏れの疑い／仕様外変更の疑いを早期にフラグ立て（断定ではなく要確認として）。
③ スケジュール予測性
AsIs
  • 影響調査に「やってみないと分からない」時間がかかり、テスト工数が読みにくい。
  • 後から影響画面が増え、リリース直前に計画が崩れることがある。
ToBe
  • 影響範囲が早期に確定するため、テスト工数の見積り精度が上がる。
  • テスト工数の初期見立てを自動算出。チェック項目を種別（表示／操作／エラー／DB必須）ごとに係数で積み上げ、準備時間とバッファ込みのレンジ（時間）で提示。
  • チェック項目数が可視化され、進捗・残量を数で管理できる。
④ 失敗からの学習・ナレッジ蓄積
AsIs
  • 前回のレビューで気づいた観点（例: DB移行の落とし穴）が、その人の記憶にしか残らない。
  • 担当者が代わると同じ見落としが再発し、品質が安定しない。
ToBe
  • レビューで得た指摘をAIが永続メモリに蓄積し、次回以降の同種PRへ自動で適用。
  • 経験が個人ではなく組織の資産として残り、メンバー交代でも品質が落ちにくい。
⑤ リリース判断の材料
AsIs
  • 「テストした／問題ない」の報告が中心で、何を確認したかが残らない。
  • リリース可否の判断根拠が属人化し、説明・監査が難しい。
ToBe
  • 確認すべき項目リスト（チェックボックス形式）が成果物として残る。
  • 消化状況が記録に残るため、品質ゲートの判断材料の一つとして活用できる可能性がある。

PM/PO が受け取る成果物

  • 仕様変更ごとに1つ、影響範囲とテスト手順をまとめたドキュメントが自動生成されます。
  • 画面別のチェックリストになっており、テスト担当へそのまま渡せます。
  • テスト工数の概算見積もり（レンジ表記）が付き、計画の初期見立てに使えます。
  • DB変更を含む場合は、データ移行・初期データの確認項目も必須として付与されます。
  • 「スコープ外」と「仕様との食い違い」が明記され、リスクの所在が一目で分かります。

役割分担 — AIと人の境界

regression-scope は「テスト範囲の確定と文書化」までを担います。 実際のテスト実施、そして最終的なリリース可否の意思決定は PM/PO・QA が行います。 AIはスコープ決めの抜け漏れと属人化をなくし、人の判断をより確実にするための土台を用意します。
タスク担い手補足
影響範囲の特定・スコープ確定AI（自動）仕様書と実装差分の両面から洗い出し
テスト手順・チェックリスト作成AI（自動）画面別に操作＋期待結果を生成
仕様と実装の食い違い検知AI（自動）「要確認」としてフラグ提示
テスト工数の概算見積もりAI（自動）項目数×係数でレンジ提示（確定値ではない）
過去知見の学習・適用AI（自動）指摘をメモリに蓄積し同種PRへ自動反映
テストの実施・結果記録人 / 別AIテスト担当・自動テストが実行
スコープ妥当性の承認PM / PO提示された範囲の最終確認
リリース可否の判断PM / PO / QA品質ゲートでの意思決定
