3エージェントの連携パイプライン

従来は開発者が「影響範囲の見極め → PR説明 → チケット要点」までを手作業・属人的に行っていた（AsIs）。これを regression-scope の確定出力を起点に、下流の pr-writer / ticket-writer へ受け渡して自動化する（ToBe）。

AsIs ― 従来（開発者が手作業・属人的）
ToBe ― 3エージェント連携（自動化）

仕様 × 実装差分 × リポジトリ から分かる4つの情報

仕様（あるべき変更）・実装差分（実際の変更）・リポジトリ（全画面）の3つを突き合わせ、regression-scope が次の4つを機械的に洗い出す。

① スコープ内の実装
仕様どおりに実装された部分。本命のテスト対象。
② スコープ外の実装
仕様にないのに変わった部分（スペック外変更）。要確認。
③ 実装漏れ
仕様にあるのに実装されていない部分。要確認。
④ 影響範囲
変更APIから波及する画面・機能。リポジトリ全体を追跡して洗い出す。
起点

regression-scope

読み手：QA・開発・PM/PO
  • Spec × git diff の2段階分析でテストスコープを自動確定
  • 要件↔実装の整合チェック（実装漏れ・仕様外変更を「要確認」で提示）
  • テスト工数を初期見立て（レンジ）
下流

pr-writer

読み手：レビュアー・開発者
  • 追加された機能・テスト観点・影響範囲を整理
  • そのまま使える PR用の文書を自動生成
  • レビューの着眼点が PR に最初から揃う
下流

ticket-writer

読み手：PM・PO
  • 作業チケットに影響範囲・テスト工数・PM向けの要点を自動でまとめる
  • 進捗・判断に必要な情報がチケットにそろう
  • 状況説明の手間と粒度のブレを削減

主要な観点での AsIs → ToBe

① テストスコープの確定regression-scope
AsIs
  • 「どこまでテストするか」は開発者の口頭報告ベース。粒度が案件・人で揺れる。
  • スコープの根拠が曖昧で、PM/PO が妥当性を判断しづらい。
  • 影響画面の数え漏れが、テスト計画の抜けに直結。
ToBe
  • 影響する画面・API・操作が一覧化され、根拠（どの変更が波及したか）付きで提示。
  • 「スコープ外」とその理由も明記され、線引きを PM/PO が確認できる。
  • 画面ごとの確認手順まで生成され、そのままテスト計画の素材になる。
② 要件トレーサビリティ（仕様↔実装）regression-scope
AsIs
  • 仕様どおり作られたか、余計な変更が無いかは、レビューで人が気づくかどうか。
  • 「仕様にあるのに未実装」「仕様外の変更」が後工程まで見過ごされやすい。
ToBe
  • 仕様書の「変わるはず」と実装の「実際に変わった」を突き合わせて差分を提示。
  • 実装漏れの疑い／仕様外変更の疑いを早期にフラグ立て（断定ではなく要確認として）。
③ テスト工数の見立て・スケジュール予測性regression-scope
AsIs
  • 影響調査に「やってみないと分からない」時間がかかり、テスト工数が読みにくい。
  • 後から影響画面が増え、リリース直前に計画が崩れることがある。
ToBe
  • 影響範囲が早期に確定するため、テスト工数の見積り精度が上がる。
  • テスト工数の初期見立てを自動算出。種別（表示／操作／エラー／DB必須）ごとに係数で積み上げ、準備時間とバッファ込みのレンジ（時間）で提示。
  • チェック項目数が可視化され、進捗・残量を数で管理できる。
④ PR文書の作成pr-writer
AsIs
  • PR説明は開発者が手書き。観点や影響範囲が書かれず、レビュー前提が共有されない。
  • レビュアーがコードから影響を推測するため、見落としと負荷が発生。
ToBe
  • 追加機能・テスト観点・影響範囲を整理した PR文書を自動生成。
  • レビュアーは「何を見るべきか」が最初から分かり、レビュー品質と速度が安定する。
⑤ チケット要点のまとめ（PM向け）ticket-writer
AsIs
  • チケットには作業メモが断片的に残る程度。影響範囲・工数・要点が集約されない。
  • PM/PO が状況を把握するのに、毎回ヒアリングと整理が要る。
ToBe
  • 影響範囲・テスト工数・PM向けの要点をチケットへ自動でまとめる。
  • PM/PO はチケットが状況把握の起点になり、説明の手間と粒度のブレが減る。

PM/PO が受け取る成果物

  • 仕様変更ごとに、regression-scope が影響範囲・テスト手順・工数見積りをまとめた基礎ドキュメントを自動生成。
  • pr-writer が PR文書、ticket-writer がチケット要点を、それぞれの読み手向けに自動整形。
  • テスト工数はレンジ表記の概算が付き、計画の初期見立てに使える。
  • DB変更を含む場合は、データ移行・初期データの確認項目も必須として付与。
  • 「スコープ外」と「仕様との食い違い」が明記され、リスクの所在が一目で分かる。

役割分担 — AIと人の境界

3エージェントは「テスト範囲の確定」と「PR文書・チケット要点の作成」までを担います。 実際のテスト実施、そして最終的なリリース可否の意思決定や取捨選択は PM/PO・QA が行います。 AIはスコープ決め・文書化の抜け漏れと属人性を大きく減らし、人の判断をより確実にするための土台を用意します。
前提と限界 ― 必ず人が確認する点
  • AIも漏らしうる：影響範囲は変更APIの横断検索（grep）で洗い出すため、動的呼び出し・設定経由・暗黙の依存は拾い切れないことがある。出力は「スコープ外／実装漏れの妥当性」「源なし項目・間接依存」の観点で PM/PO・QA が確認する。
  • 出力品質は入力（仕様）の品質に依存：属人性はゼロにはならず、「標準フォーマットの仕様を用意する」前提に移る。仕様が曖昧なら scope も曖昧になる。
