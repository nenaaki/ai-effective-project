AI Agent / Regression Scope

regression-scope エージェント
従来の人間作業の AsIs → ToBe

仕様変更が発生したとき、「どこまでデグレードチェックすれば十分か」を決める作業は、 これまで開発者の経験則と注意力に強く依存していました。 regression-scope は、その範囲特定・影響追跡・文書化を肩代わりする読み取り専用エージェントです。

読み取り専用（コード変更なし） Spec × git diff の2段階分析 テスト工数の概算見積もり 永続メモリで知見を蓄積・学習 出力: .work/{チケットID}.regression-scope.md

01ひとことで言うと

⛏ AsIs — 従来（人間）

仕様変更後、開発者が頭の中と手作業で実施
  • 属人的 仕様書を読み、影響範囲を「経験と勘」で想定
  • 手作業 git diff を自分で読み、変更APIをフロント全体から手 grep
  • 漏れる DB変更時の migrate/seed 確認を思い出せるかは人次第
  • 気づけない 仕様と実装のズレ（実装漏れ・スペック外変更）は見落としやすい
  • 読めない テスト工数は「勘でざっくり」。根拠がなく計画が崩れやすい
  • 忘れる 前回PRで踏んだ落とし穴は個人の記憶頼み。担当が変わると失われる
  • 残らない チェック手順は文書化されず、頭の中で完結しがち

✓ ToBe — regression-scope 導入後

planner の最終ステップ／単独でも起動可能
  • 体系化 Spec から「変わるはず」を予測（Phase 1）
  • 自動 git diff を層別分類し、変更APIを grep で全画面追跡（Phase 2）
  • 強制 DB変更を検知したら migrate/seed チェックを必ず出力
  • 検出 予測 vs 実装を照合し「実装漏れ?／スペック外変更?」を提示（Phase 3）
  • 見積 チェック項目を種別×係数で積み上げ、テスト工数をレンジで概算（Step 4.5）
  • 学習 過去PRのフィードバックを永続メモリに蓄積し、該当条件のPRへ自動適用
  • 資産化 画面別テスト手順を Markdown で文書出力 → frontend-tester モードR が消費

02従来作業の「どこ」を肩代わりするか

仕様変更時の人間の典型作業を分解し、各ステップを誰が担うかを示します。

従来の人間の作業 AsIs（人間がやっていたこと） ToBe（regression-scope の担当） 担い手
影響範囲の予測 仕様書を読み、「このテーブル/APIが変わるはず」を記憶ベースで想定。書き出さないことも多い。 Phase 1
specs/ の DB・API・FE スペックを読み、変更予定のモデル/Query/Mutation/画面と §9テスト観点を構造化抽出。		 AI 自動

変更API名で両アプリを横断 grep し、ヒットした画面パスと役割を特定。直接変更されたFEファイルも併せて検出。		 AI 自動
DB安全確認の想起 「マイグレーション当てた？」「reset→seed 通る？」を覚えていれば確認。新人や繁忙時に抜けやすい。 DB層に変更があれば prisma:migrate と migrate:reset → seed の必須チェックを機械的に出力。seed未変更の不整合も警告。 AI 自動
仕様↔実装のズレ検知 「仕様にあるのに実装されてない／仕様にないのに変わってる」は、よほど注意深くないと気づけない。 Phase 3
予測スコープと実差分を照合し「⚠️実装漏れ?」「⚠️スペック外変更?」を可能性として提示（断定はしない）。		 AI 自動
テスト手順の起こし 影響画面ごとに「何を操作して何を確認するか」を毎回手書き。粒度や網羅性は書き手次第。 Spec §9 を正本に、ゴールデンパス／変更点直結／DB連動値／エラーケース／境界確認の観点で操作＋期待結果セットのチェックリストを生成。 AI 自動
テスト工数の見積もり 「だいたい半日くらい」を経験と勘で口頭提示。根拠が残らず、画面が増えると計画が崩れる。 Step 4.5
チェック項目を表示／操作＋結果／エラーケース／DB必須に分類し、種別×係数＋画面ごとの準備OH＋20%バッファで積み上げ、レンジで提示。「確定値ではなく初期見立て」と前提も明記。		 AI 自動
過去知見の再利用 前回PRで踏んだ落とし穴（例: マイグレーション履歴スカッシュ時の罠）は個人の記憶頼み。担当者が代わると同じミスを繰り返す。 永続メモリ（.claude/agent-memory/regression-scope/）に feedback を蓄積し、該当条件のPRで自動適用。例: スカッシュPRでは「既存DBへ migrate deploy 不可／全員 reset 周知」を必ず出力。 AI 自動
スコープ外の線引き 「ここはたぶん影響ない」を口頭・記憶で判断。根拠が残らずレビューで再議論。 影響なしと判断した画面/機能を理由付きで明示（例: 型のみ変更でAPIシグネチャ不変、未使用Mutation等）。 AI 自動
文書化・共有 多くの場合ドキュメント化されず属人化。レビュアーは範囲を追検証できない。 .work/{チケットID}.regression-scope.md に一貫フォーマットで出力。frontend-tester モードR の入力になる。 AI 自動
実際のテスト実行・合否判断 画面を開いて操作し、デグレの有無を最終判断。 範囲は提示するが 実行はしない。実テストは frontend-tester（モードR）/ e2e-test、最終判断は人間。 人間／別AI
スコープ妥当性の承認 範囲を自分で決めて自分で納得。第三者チェックは無いことが多い。 乖離は「可能性」として提示するため、最終的な取捨選択・意思決定は人間が行う。 人間

キモは「2つの視点のズレ」。 Spec が示す「変わるはず」と diff が示す「実際に変わった」の差分そのものが品質リスクのシグナルになります。 人間が片方（多くは diff だけ）しか見ていなかったところを、両面から突き合わせる点が肩代わりの本質です。 各 Phase の入口では永続メモリの学習済み観点（後述）も併せて参照し、過去の落とし穴を自動で取り込みます。

04開発パイプライン上の位置づけ

起点は人間による要件・仕様策定（変更含む）。そこから先の実装～範囲確定（1回目）までを planner がオーケストレーションする。その後は人間が目視しながらAIに微調整させ、PR作成時に regression-scope へテスト観点を再確認させる（2回目）。最終テストは frontend-tester（モードR）の自動検証と人間による手動テストの両輪で行い、いずれも regression-scope の出力を観点として消費する。

planner の自動オーケストレーションは「要件・仕様策定の後〜1回目の範囲確定まで」。 人間が定義した要件・仕様（変更含む）を起点に、planner が db-architect → backend → frontend → regression-scope（1回目）を直列で指揮します。 その先は人間が実装・スコープを目視しながらAIに微調整を指示する Human-in-the-loop フェーズを挟み、PR作成時にもう一度 regression-scope を走らせて、微調整で変わった内容にテスト観点を追従させてからテストへ渡します。
既存画面（Specなし）にも効く。 Spec が無い場合は diff のみで分析を続行するため、過去に仕様書なしで作られた画面のデグレードチェックにも対応できます。 これにより frontend-tester は brief §7 が無くてもモードR で検証可能になります。

05使うほど賢くなる — 永続メモリ

regression-scope は memory: project を持ち、レビューで得たフィードバックを .claude/agent-memory/regression-scope/ に蓄積する。次回以降、同じ条件のPRで学習済みの観点を自動で適用する。

蓄積済みの学習例（PW-161 で獲得）: feedback-migration-squash.md — マイグレーション履歴をスカッシュ（複数 migration を 0_init に統合）するPRでは、 既存DBに migrate deploy が使えない／migrate:reset → seed でのフルリビルドが必要／チーム全員への周知が要る／main の 0_init とのテーブル数・名称差異の確認 を必ず出力に含める。

属人的だった「前回の落とし穴」が、担当者が代わっても再現される組織知として残る点が、静的なチェックリストとの決定的な違いです。 なお、コードパターン・ファイルパス・git履歴・過去の regression-scope ドキュメント内容はメモリに保存しない（再調査すれば分かるため）。
