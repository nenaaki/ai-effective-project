人間作業の AsIs → ToBe

「どこまでデグレードチェックすれば十分か」は従来、開発者の経験則に依存していました。 regression-scope が影響範囲・テスト観点・テスト工数を確定し、その出力を正本に、 下流の pr-writer（PR文書）と ticket-writer（チケット要点）が文書化を肩代わりします。

regression-scope pr-writer ticket-writer
読み取り専用（コード変更なし） Spec × git diff の2段階分析 テスト工数の概算見積もり 出力: .work/{チケットID}.regression-scope.md

01ひとことで言うと

⛏ AsIs — 従来（人間）

仕様変更後、開発者が頭の中と手作業で実施
  • 属人的 仕様書を読み、影響範囲を「経験と勘」で想定
  • 手作業 git diff を自分で読み、変更APIをフロント全体から手 grep
  • 漏れる DB変更時の migrate/seed 確認を思い出せるかは人次第
  • 気づけない 仕様と実装のズレ（実装漏れ・スペック外変更）は見落としやすい
  • 読めない テスト工数は「勘でざっくり」。根拠がなく計画が崩れやすい
  • バラつく PR説明・チケット要点は書き手次第。同じ範囲・観点を二重に手書き
  • 残らない チェック手順は文書化されず、頭の中で完結しがち

✓ ToBe — 3エージェント連携導入後

regression-scope が範囲・観点・工数を確定 → 2エージェントが文書化
  • 体系化 Spec から「変わるはず」を予測（Phase 1）
  • 自動 git diff を層別分類し、変更APIを grep で全画面追跡（Phase 2）
  • 検出 予測 vs 実装を照合し「実装漏れ?／スペック外変更?」を提示（Phase 3）
  • 見積 チェック項目を種別×係数で積み上げ、テスト工数をレンジで概算（Step 4.5）
  • 正本化 確定した範囲・観点・工数を pr-writer がPR文書へ、ticket-writer がチケット要点へ展開
  • 一貫 同じ正本を技術寄り／管理寄りの読み手に再フォーマット。手書きの二重化を排除

023エージェント連携 — 範囲確定から文書化まで

仕様変更 → regression-scope が影響範囲・テスト観点・テスト工数を確定（正本を出力）→ その出力を下流2エージェントが消費し、読み手別の文書へ展開する。

キモは「2つの視点のズレ」。 Spec が示す「変わるはず」と diff が示す「実際に変わった」の差分そのものが品質リスクのシグナルになります。 人間が片方（多くは diff だけ）しか見ていなかったところを、両面から突き合わせる点が肩代わりの本質です。 ここで確定した範囲・観点・工数が、pr-writer / ticket-writer の正本になります。

05開発パイプライン上の位置づけ

起点は人間による要件・仕様策定（変更含む）。実装～範囲確定（1回目）までを planner がオーケストレーションする。その後は人間が目視しながらAIに微調整させ、PR作成時に regression-scope へテスト観点を再確認させる（2回目）。確定した範囲・観点・工数は pr-writer / ticket-writer が読み手別の文書へ展開し、最終テストは frontend-tester（モードR）の自動検証と人間の手動テストの両輪で行う。

PR作成時に文書化が分岐する。 2回目の regression-scope で確定した範囲・観点・工数を正本に、pr-writer がPR本文（追加機能・テスト観点・影響範囲）を技術寄りに、 ticket-writer がチケット要点（影響範囲・テスト工数・PM向け要点）を管理寄りに、それぞれ生成します。手書きの二重作業はここで消えます。
既存画面（Specなし）にも効く。 Spec が無い場合は diff のみで分析を続行するため、過去に仕様書なしで作られた画面のデグレードチェックにも対応できます。 これにより frontend-tester は brief §7 が無くてもモードR で検証可能になります。
