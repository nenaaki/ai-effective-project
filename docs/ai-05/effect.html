受入テスト設計AI — インプット品質 × 出力効果の尺度

対象: V字 ⑧受入テスト ／ ai-05/index.html の派生分析
本資料は ai-05/index.html で示した V字モデル右上の ⑧受入テスト ブロックに配置された 受入テスト設計AINEW に焦点を当て、要件定義成果物および外部インプットの品質次元が、 生成される受入基準（Gherkin）の5 軸の効果尺度 （A 網羅率 ／ B 正確性 ／ C 下流効果 ／ D 設計品質 ／ E トレーサビリティ） にどう影響するかを推論・可視化する。 数値はベンチマークではなく、現状の生成AIの一般的挙動から導いた推定値であり、 トレーサビリティAI／仕様一貫性レビュワーAIによる継続計測の初期想定値として用いる前提。
① 受入テスト設計AI の I/O 構造（誰から何を受け、何を出すか）
左＝要件定義フェーズ成果物（① 要件定義 から派生）／中央＝受入テスト設計AI／右＝受入基準（Gherkin）
※ 外部インプット「ユースケーステスト」はフェーズ外から要件定義に流入する一次資料で、シナリオ派生の骨格となる。

② 出力の効果を測る品質尺度（網羅率 × 正確性）
受入テスト設計AIの効果は 5 軸 で測る。 上段＝A 網羅率（要件のうちどれだけシナリオ化できたか）／B 正確性（業務的に正しい表現か）— "Gherkin そのもの" の品質。 下段＝C 下流効果（後工程・本番への効き）／D 設計品質（テスト技法・配分の質）／E トレーサビリティ（漏れ・浮き・層間ドリフトの可視化）— "受入テスト設計AIを置く意義" を示す指標群。
A. 網羅率（Coverage）— どこまで尽くせたか
未対応要件・浮きシナリオを検出するための「量」の尺度。トレーサビリティAI が常時可視化する。
A1. 機能要件カバレッジ
= シナリオで検証される機能要件数 / 機能要件総数
機能要件一行一行に対し、最低1本の Gherkin シナリオが紐付くか。主インプット＝機能要件。
A2. 業務ルール網羅率
= 検証された業務ルール数 / 業務ルール総数
業務ルール一覧の各ルールが正常系/異常系シナリオで踏まれているか。主インプット＝業務ルール一覧。
A3. ユースケーストレース率
= UC↔シナリオ対応数 / ユースケース総数
外部インプット「ユースケーステスト」と Gherkin の対応関係。トレースマトリクスの埋まり方。
A4. 非機能要件カバレッジ
= 性能/可用性/セキュリティ等の検証数 / 非機能要件項目数
受入テストで検証可能な非機能（応答時間・同時接続等）に閾値ベースのシナリオが生成されたか。
A5. シナリオパターン網羅率
= 各機能における (正常系 + 異常系 + 境界値) ÷ 3
機能ごとに 3 パターンが揃っているか。異常系・境界値の漏れを検出する指標。
B. 正確性（Accuracy）— どれだけ業務的に正しいか
業務SMEの承認段階・E2E実装段階で発覚する手戻りの量から、生成内容の「質」を測る尺度。
B1. 業務SME修正率
= 修正されたシナリオ行数 / 生成シナリオ行数
業務SME 承認時に書き換えられた割合。AI の業務理解度の総合指標。
B2. 用語整合率
= 用語集に合致する語の出現数 / 専門語の総出現数
用語集と Gherkin の用語が一致するか。揺れがあると下流（E2Eテスト実装AI）に伝播。
B3. シナリオ実行可能率
= E2E化できたシナリオ数 / 生成シナリオ総数
構文的に有効で、Given / When / Then が E2Eテスト実装AI で具象化できるか。
B4. 業務ルール再現率
= ルール通り表現されたシナリオ数 / ルール参照シナリオ数
業務ルールの条件分岐や閾値が、シナリオの Given/When に正しく落ちているか。
B5. 偽陽性率
= 要件外シナリオ数 / 生成シナリオ総数
要件にない動作を勝手に検証してしまうシナリオ（AI 幻覚）の割合。
C. 下流効果（Outcome）— 後工程・本番でどれだけ効いたか
受入テスト設計AIを置く"経営的価値"を直接示す結果指標。A/B は中間指標、C は最終指標。
C1. 欠陥流出率
= UAT/本番で発見されたバグ数 / 全機能数
受入基準ですり抜けて本番に出てしまった欠陥。受入テストの究極の存在価値。
C2. E2E実装AIへの引き渡し成功率
= 修正不要で E2E化できたシナリオ / 全シナリオ
B3 が「構文的に有効か」なのに対し、これは下流AIの実装視点から見て直接使えるか。
C3. SMEレビュー時間短縮率
= 1 - (ToBe レビュー所要時間 / AsIs)
業務SMEの工数削減量。ai-04 の工数比較と同じ思想で左シフトのリターンを測る。
C4. 上流差し戻し率
= 受入テスト→要件定義への差し戻し件数 / 全シナリオ
⑧→① のエスカレーション発生頻度（ai-05/index.html エスカレーション表）。健全性指標。
D. 設計品質（Design Quality）— "テスト技法"の質
A5 の「3 パターン」を超えて、テスト設計の正統技法がどれだけ意識的に適用されたかを測る。
D1. テスト技法適用率
= 適用された技法種類数 / 適用すべき技法数
同値分割・境界値・状態遷移・デシジョンテーブル・ペアワイズ等が適切に使い分けられているか。
D2. リスクベース重み付け率
= 高リスク領域の検証密度 / 低リスク領域の検証密度
"量"ではなく"配分"の指標。重要な業務領域・データに検証が集中配分されているか。
D3. シナリオ独立性 / Step DRY 度
= 共通Step利用率 = 再利用Step数 / 総Step数
Gherkin の Background / 共通 Step が活用され、シナリオ間で重複していないか。保守性に直結。
E. トレーサビリティ — 漏れ・浮き・ドリフトの可視化
ai-05/index.html の トレーサビリティAI／仕様一貫性レビュワーAI の主役指標。横断AIの存在意義を直接示す。
E1. 浮きシナリオ率
= 要件IDに紐付かないシナリオ数 / 全シナリオ
AI が要件にない動作を勝手に生成した割合。B5 と類似だが、こちらはトレース不能に焦点。
E2. 孤立要件率
= シナリオが1本もない要件 / 全要件
A1 と表裏だが、運用上は別指標として可視化したい：「未充足要件」のアラート軸。
E3. 層間整合率
= 設計レーン↔テストレーンで整合確認された要素 / 全要素
仕様一貫性レビュワーAIが用語／ルールのドリフトなしと判定した割合。実装着手前に高めたい。

④ インプット品質レベル別の推論シミュレーション（出力尺度の推定値）
