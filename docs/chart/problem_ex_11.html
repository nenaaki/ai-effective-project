担当範囲 — 症状と原因の間

作るのは engineer、壊れていることを見つけるのは tester。その間は今まで誰の担当でもなかった。

位置づけ 2 / 3

3つの軸 — 実行・来歴・外的要因

症状の1点から3方向へ探す。3つ目の「自分の外で状態が変わった」は差分にも自分のコードにも現れない — ここを見ないとコードをいくら読んでも当たらない。

実行 — 測る

  • 各層に実際の値を取る手段がある。推論せずそれを打つ
  • ③から始めると1手で上下どちらかが無罪になる

来歴 — 辿る

  • 直前に正本を開いていない → 制約を見ずに実装している
  • 未解決の業務論点にヒット → 不具合ではない。人へ返す

外的要因 — 突き合わせる

  • 環境は調査の最初のゲートで潰す
  • 降ってきた変更は症状の場所と交差するかを見る

束ねるのは機械、どこがズレの起点かを読むのはAI、直すか業務論点として戻すかを決めるのは人。この分界は崩さない。

位置づけ 3 / 3

権限 — 一時変更が許される唯一のエージェント

tester 系は読み取り専用、engineer 系は spec 駆動。debugger はどちらでもない — 値を推測せず取るため、観測用のコードを仕込んでよい。

できること

  • 観測のために一時的なログを仕込むデバッグ終了時に必ず戻す
  • 検証用データを自分で作り、自分で消す
  • 自分では再現できないときだけ、画面の写真を人に頼む

できないこと

  • 恒久的な修正を確定する診断書を engineer へ渡す。人が「そのまま直して」と言った場合のみ例外
  • 仕様・期待値を決める（テストの期待値を実装に合わせて緩めるのも同じ）
  • 既存データを書き換える・消す（壊れたデータも潰さない＝証拠）
  • 再現していない状態で修正を提案する

仕込んだものは戻してから報告する（差分が空であることを確認）。記憶に頼ると必ず残る。個人情報はログに出さない — 出してよいのは件数・型・有無だけ。

工程 1 / 5

全体像 — 通してはいけないゲートと、抜ける出口

線形に見えるが、効いているのは通してはいけないゲートとengineer に渡さず抜ける出口。

ゲートを通す条件

  1. 環境ゲート — 前提チェックと経路疎通が通る（有効な観測を引き継げるならスキップ可。人間からの報告は必ず通す）
  2. 再現ゲート — 再現手順が1コマンドで打てる。ゆらぐなら測定へ、ローカルで出ないなら環境差へ
  3. 因果ゲート — ①症状までの経路を端から端まで説明できる ②原因を出し入れして症状を ON / OFF できる

2 が満たせないなら、まだ見つけていない。ここを緩めると「触ったら消えた」が完了報告になる。

仮説台帳は「仮説」と「それを否定する最小の観測」をセットで書く。順序は確からしさ × 安さで、棄却した仮説も消さない（書式は仕様書側）。

工程 2 / 5

Step 1 環境ゲート — 調査を始める資格

環境が通っているか確かめる前に、症状の話を始めない。一番よく溶けるのは前提が壊れたままロジックを疑っていた時間。

何を見るか

  • サービスが動いているか（ポートとプロセスの両方）
  • 自動生成コードがソースに追いついているか
  • ビルド成果物が上書きされていないか
  • DB の適用状態（未適用・履歴の分岐）
  • 設定の欠落・タイムゾーン・作業ツリーの中断
  • 直近に降ってきた変更（自分の差分には出ない）

引き継いだ観測が切れる条件

  • 本流の取り込み
  • DB 更新・データ再投入
  • ビルド・コード生成
  • 時間経過・別セッション

どれかに触れたら引き継がず打ち直す。

続けて既知の失敗モードを症状で引く。載っているのは症状と原因の場所が離れているものばかりで、症状からコードを読み始めても当たらない。ただし前提が壊れていても、そこで終わりにしない — 直したことは症状が消えた証明にならない。環境が原因だったのか、環境に隠れて別の不具合があるのかは、こちらでは分からない。

工程 3 / 5

Step 2 問診 — 自然文を再現手順に変える

「TC-XXX が落ちる」の形を人間に要求しない。人は「荷受けでスキャンしても進まない」と言う。それが正常な入口で、変換するのは debugger の仕事。

再現コマンド: <1行>
環境:         <local / stg / 報告者の手元。commit・seed の状態>
期待:         <何が起きるべきか>
実際:         <何が起きるか。原文のまま>
再現率:       <n/n 回>

満たすべき条件は決定論的（3回打って3回同じ）・最小・速いこと。ゆらぐならそれ自体が最初の症状。

再現できないときはそこで止めて人に返す。「多分ここだろう」で直すのは、直ったか判定する手段がないまま変更を入れるということ。

情報人に聞くか
起動状態・生成物の鮮度・DB の適用状況聞かない
画面のエラー・通信の失敗聞かない
API のエラーコード・スタックトレース聞かない
誰の・どの判断で書かれたか聞かない
直近の取り込み・履歴の巻き戻し聞かない
何が起きるべきだったか（期待値）必ず聞く
どう操作したか推測できないときだけ
前は動いていたか・いつからか聞く

機械で取れることを人に聞かない。ただし期待値だけは代替不能 — 人にも分からず正本にも無いなら、それはバグではなく業務論点。

工程 4 / 5

ゆらぎの原因を突き止める — 何が結果を変えているか

3回打ってそろわないのは「再現できない」ではなく、何かが結果を変えているという情報。何が変えているのかを先に決める — よくあるのは次の3つで、それぞれ調べる先が違う。

① 時間と順序が変えている

  • 再現率と失敗の偏りを測る
  • 偏り＝初回だけ／後半に集中／時間切れ
  • → タイムアウトと無応答時の振る舞いを調べる

② 環境が変えている（ローカルで出ない）

  • 環境差を安い順に1つずつ持ち込む
  • 症状が出たら、そのとき持ち込んだ差分が原因
  • → インフラとエミュレーターの仕様を調べる

③ 同時に動くものが変えている

  • 相手は人の操作とは限らない（未着手／実行中／完了後）
  • 足並みをそろえて同時に撃つ
  • → 処理のシーケンスを調べる

原因に迫ったら論理的な修正案まで出す。ただしこの種の不具合には、どうやっても防げない条件が必ず残る — そのとき利用者のデータをどう守るか（失敗側に倒す／後から突合して直す／記録だけ残す）は業務の判断なので、決めずに人へ返す。

どれにも当たらないなら人へ返す。自分の環境で再現しないことは、不具合が無いことの証明ではない。

工程 5 / 5

Step 3 層の bisect — 打つものと、割れる範囲

推論せず観測する。③から始めると1手で範囲が半分になる。使い捨てのスクリプトは書かない。

「前は動いていた」ならコミット方向にも境界がある。ただしその前に⑦の履歴を見る — 取り込みが症状の場所と交差していれば、全体を二分探索せず2点比較で境界が出る。

出口

出口 — 何を残し、どこへ渡すか

仕様が決まっていないものは engineer へ渡さない（渡すと実装で決めた仕様が既成事実になる）。

原因の種類渡す先
バックエンドの実装バグbackend-engineer
画面側の実装バグfrontend-engineer
DB スキーマ / マイグレーションdb-architect
テストの期待結果自体が誤りtest-spec-designer
仕様が決まっていない業務論点へ
環境・設定人 ＋ 既知の失敗モード表へ1行
テスト環境でだけ再現する人。どの差分で再現したかを明記（未特定なら「未特定」）

打ち切り

仮説を5件棄却しても確定しないときは、台帳を持って人に返す。最大の損失は誤診ではなく誤診に気づかないまま編集を重ねること。ゆらぐものは件数では止まらないので時間で打ち切る（既定5分）。

やってはいけない

  • 例外を握りつぶす／リトライ・待ち時間で「たまたま通る」状態にする
  • 再現していない状態で修正を提案する
  • 「おそらく〇〇が原因です」「たまに出る」で報告を終える
  • ゆらぐ症状で、1回通っただけで「直った」と言う
  • 一時的な観測コードを戻し忘れる

稼働実績 — まだ少ない

定義の確定以降の起動は3件、いずれも同一チケットの再テスト中。全件が診断を返した一方、2件目は直前のマージを疑えず誤診し、3件目で自ら訂正した。環境ゲートはこの誤診から入れたチェック。「原状回復済み」は自己申告で、第三者検証ではない。
