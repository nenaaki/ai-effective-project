# 結合テスト・シナリオテストのAI駆動（議題）

出典：議事まとめ 2026-09-17、同日の結合テスト分析（9画面125件・3日分のセッションログ）。イテレーション4 スコープ③④に対応。

結論：AIがテストを実施できることは実証済み。次に決めるのは、実施をどう資産に変えるか。3つの柱はいずれも入口をシナリオの妥当性確認に置く。

前提（実測）：125件に Bash 1,448回、成果物はテスト結果のみ。人の台帳との一致率81%。NG 61件中31件は製品の欠陥ではない。シナリオの精度は8〜9割で、インプットが正しい前提で自動化してはいけない。

## 1. 再現性のあるシナリオ取込

- WHAT：人が書いたシナリオを、AIが毎回同じ解釈で読める形に取り込む。曖昧さ・仕様との乖離は差し戻す。
- WHY：解釈が揺れると、結果の差が製品の変化か解釈の揺れか分からない。唯一の誤OKも期待値が自然文のままだったことが原因。
- HOW：期待値をチェックリストへ分解し、正本を取り込み時に固定。全自動の前に、人がAIアシストで数件通す関門を置く。

## 2. 構築と管理

- WHAT：実施内容をテストスクリプトとして書き出し、2回目以降は実行で済ませる。書き出しは実施の副産物とし、人の工程にしない。
- WHY：回数が出るのは再テスト側。そこが毎回AI実施では単価が下がらない。壊れていないことの確認にAIの判断力は要らない。
- HOW：仕様を先頭・結果の遷移を末尾に持つスクリプトを GitHub に保存。秘匿値のマスキングを全経路に入れる（パスワードが平文でログに残る事故が発生済み）。

## 3. 仕様の網羅範囲の確認

- WHAT：シナリオと実装を突き合わせ、未検証の範囲を抽出してPMへ報告する。仕様変更から再実行対象を絞る。
- WHY：足りていない範囲は現状そもそも誰も見ていない。変更のたびに全件実行か勘で絞るかの二択になっている。
- HOW：画面・API × シナリオの網羅状況を可視化。並行可否で使った「書く表／読む表」の判定を、実装からの機械的な導出に置き換える（現状53画面中7画面のみ手作業）。

後段（NG対応・原因分析＝スコープ④）へは、根本原因IDによるNGの分離と、バグ密度・テスト密度の差し戻しで接続する。構成は複雑にしない。

## 残っている論点

- いつスクリプトへ固定するか。OK率39%の現状で早すぎると仕様変更で落ち続ける。
- 人の台帳との一致率を精度指標として使い続けるか（AIのほうが仕様に忠実でも減点される）。
- シナリオの正本不在はテスト側では解けない。仕様側の整備として別に立てるか。
