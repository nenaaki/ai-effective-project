プロセス（起票 → 合意 → 実装 → 承認）

⚠ 変更管理の場合の注意点

ドラフトチケットの例①（外部基幹システム連携基盤）

PW-210開発
外部基幹システム連携基盤（ファイル連携の共通基盤）を構築する

概要

PW基幹・サイサン様との出荷指示の受信／出荷実績の送信（先行4本）を、ファイルでやり取りするための共通の土台（外部基幹システム連携基盤）を作る。授受方式（SFTP）・時刻起動・ファイル形式の定義が4本とも共通のため、個別に作らず共通の土台に乗せる。各やり取りのデータ項目の取込・送信そのものは別チケットの担当で、本チケットは土台に閉じる。

内容

実現したいこと（何を作るか）:
  1. ファイルの置き場（授受）— AWS・ローカルの2軸
    • AWS側: 連携相手がSFTPでファイルを置く・取るための置き場（S3バケット＋AWS Transfer Family）を用意する
    • ローカル側: 開発環境でも同じ動作をする置き場（Docker上のSeaweedFS・S3互換）を用意し、同じバケット名・フォルダ構成で動かせるようにする
    • 処理済み・エラーのファイルは所定のフォルダへ退避し、後から追跡できるようにする
  2. 取込の流れ（受信側）
    • 決まった時刻に自動起動 → 置き場からファイル取得 → 形式チェック → PW-DMSのデータへ登録 → 後続処理（配送指示書の作成）をキック
  3. 送信の流れ（送信側）
    • 決まった時刻に自動起動 → 対象データを抽出 → ファイル生成 → 置き場へ配置
  4. ファイル形式の定義
    • 項目構成・ヘッダー/明細の構造・区切り方・文字コードを「形式ごとの定義」として持ち、定義を足すだけで新しいやり取りを追加できるようにする
  5. 異常時の挙動
    • 一部データの異常・同一ファイルの重複配置のとき、合意した挙動（要確認事項2・3）どおりに安全に倒れ、通知する
仕様（該当箇所の転記）:

出所: PW-DMS_要件定義書_機能一覧_1.00.xlsx「共通基盤一覧」シート／PW-DMS_IF項目定義書_v0.1.xlsx「インターフェース一覧」シート

  • 基盤の前提（共通基盤一覧「外部基幹システム連携基盤」・最優先マーク）

    外部の各基幹システムと双方向の情報連携を行うための基盤

    【前提】S3バケットにTransferFamilyを用いたSFTPアクセスを可能とし、各基幹システム担当者様がファイルの送受信を行えるようにする。

  • 出荷指示取込（同上）

    1. 特定の時間に取込処理をキック、S3バケットから取込用ファイルを取得し、各種バリデーションとデータマッピングを行った上でPW-DMSのDBに登録。
    2. 配送指示書の作成処理をキック

  • 出荷実績送信（同上）

    1. 特定の時間に送信処理をキック、PW-DMSのDBから対象データを取得し、出荷実績ファイルを生成。
    2. S3バケットに出荷実績ファイルを配置。

  • 運用時刻の手がかり（IF項目定義書・備考抜粋）

    PW出荷指示データ受信: 毎営業日ごとに受信。お水以外は10:30-11:00にアップロード、お水は11:30-12:00にアップロード、12時台に処理実施、14時頃までに配送指示書を出力。

    PW出荷実績データ送信: 毎営業日ごとに送信。出荷実績データは基本的に15時までに作成してSFTPに格納。前日出荷分・当日出荷分を合わせて「出荷日」当日に実績データを生成して格納。

作り方の方針（合意すべき範囲・前提）:
項目方針
対象範囲先行4本（PW出荷指示受信・PW出荷実績送信・サイサン出荷指示受信・サイサン出荷実績送信）が乗る土台。個々のデータ項目の取込・送信ロジックは対象外（別チケット）
授受方式AWS Transfer Family（マネージドSFTPサービス）をS3バケットに直結。連携相手ごとにSFTPユーザーを分け、アクセス範囲をその相手専用のフォルダに限定する
環境の2軸AWS側＝S3＋Transfer Family／ローカル側＝SeaweedFS（Dockerに組み込むS3互換ストレージ。選定理由: S3との互換性が高く、無料）。同じバケット名・フォルダ構成・同じ処理コードで両環境が動き、接続先は環境変数で切り替える。SFTPの入口はAWS側のみ（ローカルはS3互換APIへ直接ファイルを置いて代替）
置き場の構成環境ごとに連携用S3バケットを1つ。フォルダは相手別×方向別に分け、処理後は処理済み／エラーへ日付付きで退避（具体構成は下記）
定刻トリガーと実行基盤定刻起動はAmazon EventBridge Scheduler（採用合意済み）。実行本体はAmazon ECS（AWS Fargate）のタスクをEventBridge Schedulerから直接起動（RunTask）し、api-coreと同じコードベースのコンテナをジョブ用コマンドで実行する（要確認事項9）。AWS Lambdaは不採用（取込・生成の処理時間が上限15分を超えうる・ローカル再現性）。AWS Batch（同名のマネージドサービス）も不採用（ジョブキュー等の機構が日次実行には過剰。本文の「バッチ」は処理方式の意味で、このサービスを指さない）。AWS Step Functionsも今回は不採用（処理は1コンテナ内で完結する逐次処理で、失敗時はジョブ丸ごと再実行＋冪等スキップで足りる。フロー定義がアプリ外に出るとローカル同一動作の再現と相性が悪い）。ただし将来の並列制御（帳票のデポ別並列など）に備え、EventBridge Scheduler→Step Functions→ECSタスクへ差し替え可能なよう起動入口は薄く保つ。ローカル側はアプリ内スケジューラまたは手動コマンドで起動。実行結果は既存のバッチ実行記録に残す。起動時刻は要確認事項1
バリデーションの分担形式チェック（文字コード・列数・型・必須）は基盤の共通機能として持ち、業務チェック・項目マッピング（値の読替・マスタ存在確認など）は各IFチケットの定義側に置く。基盤に個別の業務ルールを持ち込まない
ファイル名の扱いファイル名のパターンも形式定義の一部として持つ。受信では対象ファイルの特定に使い、送信では現行の受け渡しファイル名を踏襲して生成する（正確な命名は各IFチケットのレイアウト突合で確定）
形式の持たせ方ファイルの形式（項目構成・ヘッダー行と明細行の構造・区切り方・文字コード）を「形式ごとの定義」として持たせ、新しいやり取りの追加時は定義を足すだけで済む作りにする
対称性取込側（受信→検証→取り込み→後続処理の起動）と送信側（対象データの抽出→ファイル作成→置き場所への配置）を、同じ骨組みの表裏として作る（片方だけ特殊な作りにしない）
既存の作りとの接続点出荷指示の取込完了後は、配送指示書の作成処理を起動する入口を担う（配送指示書そのものの生成は帳票側の基盤の担当）
処理の流れ（受信・送信の端から端まで・どの層が担うか）:

受信（取込）:

手順内容担う場所
1基幹担当者がSFTPでファイルをアップロード（Transfer Family経由でS3の {相手}/in/ に格納）AWS設定（本チケット）
2定刻トリガー（EventBridge Scheduler）が取込バッチを起動AWS設定＋基盤
3バッチが in/ からファイルを取得（ファイル名パターンで対象を特定）基盤
4形式チェック（文字コード・列数・型・必須）基盤（共通バリデーション）
5業務チェック＋項目マッピング（値の読替・マスタ存在確認など）各IFチケット（定義）
6DBへ登録（トランザクション）基盤の枠＋各IFの定義
7ファイルを processed/（失敗時は error/）へ退避基盤
8後続処理（配送指示書の作成）をキック基盤（入口のみ）
9実行結果をバッチ実行記録へ記録、異常は通知基盤

送信:

手順内容担う場所
1定刻トリガー（EventBridge Scheduler）が送信バッチを起動AWS設定＋基盤
2DBから対象データを抽出（抽出条件は各IFの定義）基盤の枠＋各IFの定義
3形式定義に従い実績ファイルを生成（cp932・ヘッダー/明細・現行踏襲のファイル名）基盤＋各IFの定義
4S3の {相手}/out/ へ配置（基幹担当者がSFTPで取得）基盤
5実行結果をバッチ実行記録へ記録、異常は通知基盤
置き場の構成（提案・管理者が実環境で確認する情報）:

現状S3の利用は無く本基盤が初出のため、命名はここで決めたものを正とする。

  • 連携用S3バケット: 環境ごとに1つ、pw-dms-external-{環境}（例: pw-dms-external-prod ／ pw-dms-external-stg ／ pw-dms-external-dev）
pw-dms-external-{環境}/
├─ pw/
│  ├─ in/                    # PW基幹 → PW-DMS: 出荷指示ファイルの置き場（SFTPアップロード先）
│  │  ├─ processed/YYYYMMDD/ # 取込成功後の退避先
│  │  └─ error/YYYYMMDD/     # 取込失敗の退避先
│  └─ out/                   # PW-DMS → PW基幹: 出荷実績ファイルの置き場（SFTPダウンロード元）
└─ saisan/
   ├─ in/                    # サイサン出荷指示（PW様経由でアップロード）。processed/error は pw と同構成
   └─ out/                   # サイサン出荷実績
  • SFTPユーザー（Transfer Family）: 連携相手ごとに1ユーザー（pw-foru ／ saisan）。ホームディレクトリを当該相手のフォルダに固定し、他相手のフォルダにはアクセス不可とする
  • KSLが後発で加わる際は ksl/ フォルダとSFTPユーザーの追加のみ（バケットは増やさない）
  • 同じバケット名・フォルダ構成をローカルのSeaweedFSにも作成する（ローカル側でも名前の定義が必要なため、命名はここで確定させる。ローカルのバケット名は pw-dms-external-dev を使用）
  • バケット名・フォルダパス・接続情報は環境変数で持ち、コードに直書きしない
スコープ外（やらないこと）:
  • PW出荷指示データ受信・PW出荷実績データ送信・サイサン出荷指示データ受信・サイサン出荷実績データ送信、それぞれの実データ項目の取込・変換・送信ロジックの実装（別チケット）
  • KSL出荷指示データ受信（授受方式が相手方と調整中のため後発。方式確定後に本基盤へ定義を追加する形で対応）
  • 指定場所配送NGフラグ連携・解約新規案件の情報引継ぎ（今回の4本の対象外の基幹連携）
  • ローカル開発環境でのSFTP入口の再現（ローカルはS3互換APIへ直接ファイルを置いて代替する。SFTP経由の実挙動はAWS環境で確認）
  • SFTPのアクセス権限・鍵管理など、インフラ側の詳細な設定作業

要確認事項（合意が必要な論点）

#論点現状回答
1取込バッチは13:00、送信バッチは15:30の自動起動とする、でよいか定義書には「お水以外は10:30-11:00・お水は11:30-12:00にアップロード、12時台に処理実施、14時頃までに配送指示書出力」（受信側）、「出荷実績は基本的に15時までにSFTPへ格納」（送信側）との記載はあるが、自動処理を起動する具体時刻そのものは未確定☐ Yes ／ ☐ No
2ファイルの一部データが異常だった場合、異常な行だけを棄却して正常な分は取り込み、棄却したことを通知する、でよいか定義書に明記なし（もう一方の考え方は「ファイル全体を棄却」）☐ Yes ／ ☐ No
3同じファイルが誤って重複して置かれた場合、取り込み済みと判定できるものは再度取り込まずスキップし、その旨を通知する、でよいか定義書に明記なし☐ Yes ／ ☐ No
4サンプルの無いサイサン出荷実績データ送信も、他と同じcp932（Shift-JIS）で送る、でよいか実データサンプル（PW出荷指示・PW出荷実績・サイサン出荷指示）はいずれもcp932（Shift-JIS）☐ Yes ／ ☐ No
5ファイル連携の異常（取込失敗・送信失敗）の通知は、別途整備中の通知基盤（GoogleChat想定）に乗せる、でよいか要件定義書の「通知基盤」はエラー発生時のメッセージ通知をGoogleChatへ送る想定として別途整備中☐ Yes ／ ☐ No
6KSL出荷指示データ受信は後発、指定場所配送NGフラグ連携・解約新規案件の情報引継ぎは対象外、という認識でよいか指示書（2026-07-14）の確定事項どおり☐ Yes ／ ☐ No
7土台の実証は、実データサンプルがあるPW出荷指示データ受信（取込）を主軸に、PW出荷実績データ送信（送信側の対称構成）を合わせて、ファイル配置から登録・ファイル生成までの一連の流れを通す形で行う、でよいか詳細は完了条件を参照（受信のみで済ます案もあるが、送信側の確認が漏れる）☐ Yes ／ ☐ No
8ローカル開発環境ではSFTPの入口は再現せず、S3互換APIへ直接ファイルを置いて代替する、でよいかローカルの置き場はDocker上のSeaweedFS（S3互換）。SFTP経由の実挙動の確認はAWS環境で行う☐ Yes ／ ☐ No
9取込・送信の実行本体はAmazon ECS（AWS Fargate）のタスク（api-coreと同じコードベースのコンテナ）とし、AWS Lambda・AWS Batch・AWS Step Functionsは使わない、でよいか定刻トリガーのEventBridge Schedulerは合意済み。Lambdaは処理時間の上限（15分）とローカル再現性で不利。AWS Batchはジョブキューが日次実行には過剰。Step Functionsは1コンテナ内で完結する逐次処理には不要（冪等な丸ごと再実行で代替。将来の並列制御に備え差し替え可能な入口は残す）☐ Yes ／ ☐ No

完了条件（受け入れ観点｜目的トレース）

※ここでの完了条件は着手前の骨子。実装が完成に近づいた段階で具体的なテストデータ・期待結果に更新し、あらためて合意する。

目的「各基幹システムとのファイル授受をSFTP経由で行える」の確認:
  • 決められた置き場所（SFTP経由でアップロードできる場所）にPW出荷指示データの実データサンプルを配置すると、決めた時刻に取込処理が動き、ファイルの内容がPW-DMS側に取り込まれる（PW出荷指示データ受信を代表として、ファイル配置から登録までの一連の流れを1本通す。データ項目ごとの正確な取り込み内容は個別チケットで確認する）
  • PW出荷実績データと同じ構造（ヘッダー行・明細行の形式、文字コード）のファイルが、送信側の仕組みによって決められた置き場所に作られる（送信側の対称構成の確認。項目ごとの正確な内容は個別チケットで確認する）
目的「ローカルでも同じ動作で開発・検証できる」の確認:
  • ローカル開発環境（Docker上のSeaweedFS）でも、同じバケット名・フォルダ構成のまま、取込・送信の一連の流れが最初から最後まで通る
目的「形式ごとの定義を足すだけで新しいやり取りに展開できる」の確認:
  • 相手も形式も異なる別のやり取り（サイサン出荷指示データ受信）を、同じ仕組み（同じバッチ・同じ処理の流れ）の上で扱える作りになっていることが、実装内容から確認できる（サイサン側の実データ処理そのものは個別チケットで確認する）
目的「異常時に合意した挙動どおり安全に倒れる」の確認:
  • 一部のデータ行が壊れたファイルを取込ませると、要確認事項2で合意した挙動（正常分のみ取込／全体棄却）どおりになり、要確認事項5で合意した先に異常が通知される
  • 同じファイルを誤って2回配置しても、要確認事項3で合意した挙動どおり重複して取り込まれない
  • 動作確認（自動・手動の検証）がすべて完了していること

備考

  • 完了条件で実証に使うやり取りの組み合わせ（受信のみか、受信＋送信か）は要確認事項7で確定する。
  • 各やり取りのデータ項目レベルの正確性（項目マッピング・値変換）はこのチケットの対象外。PW出荷指示データ受信／PW出荷実績データ送信／サイサン出荷指示データ受信／サイサン出荷実績データ送信の個別チケットで確認する。
  • KSL出荷指示データ受信は、授受方式が確定した段階で、新しい基盤を起こすのではなく本チケットで作る土台へ定義を追加する形で対応する想定。

ドラフトチケットの例②（お知らせ一覧のロール別表示）

notice-list-role-access課題
お知らせ一覧のロール別 表示範囲の出し分け

概要

  • トップメニューの「お知らせ一覧」は、ログインユーザーのロール（権限グループ）に応じて表示範囲を出し分ける。
    • システム管理者や物流本部の運用管理者には全件を見せ、デポ運行管理者やOEM先・KSLの運用管理者には自分の担当範囲（自デポ／自荷主）に関係するお知らせだけを見せ、サーバー管理部やカスタマーサポートなどお知らせを見る立場にないロールには一覧そのものを見せない。本チケットでは、この「どのロールに・何を・どの範囲まで見せる／見せないか」を業務仕様を合意したのち実装する。
  • 権限グループごとのアクセス可否・範囲を管理する認可基盤に対して、「お知らせ一覧」向けの設定（ロールごとの許可範囲）を確定することが本チケットの目的である。ルート保護やAPI側の絞り込み処理そのものの実装は別スコープとする。

内容

実現したいこと（何を作るか）:

トップメニューの「お知らせ一覧」を、ログインユーザーのロールに応じて「全件」「自デポのみ」「自荷主のみ」「非表示」を出し分けられるようにする。

仕様

実装範囲（シナリオ上の作用・正常系／異常系）:

シナリオ: ユーザーがトップメニューを開くと、自分のロールに応じた範囲のお知らせエリアが表示される（画面遷移は発生せず、既存お知らせエリアの表示内容が変わるのみ）。

区分ケース期待挙動
正常系全件ロールが開く掲載期間内の全お知らせが表示される
正常系自デポ／自荷主ロールが開く自分の担当範囲が掲載対象のお知らせのみ表示される
正常系添付ファイル付きお知らせ閲覧可能な範囲内であればダウンロードできる
異常・境界禁止ロールが開くお知らせエリアが表示されない
異常・境界担当範囲に一致する掲載対象が無いスコープ限定ロールには1件も表示されない（0件）
異常・境界自デポ／自荷主ロールで所属デポ・所属荷主が未設定0件（便宜上の全件表示はしない）
異常・境界掲載期間外（開始前・終了後）ロールに関わらず表示されない（既存挙動を維持）
作り方の方針（合意すべき範囲・前提）:
項目方針
対象画面管理画面トップメニューの「お知らせ」エリア（一覧閲覧・行クリックでの詳細表示）
APIによる情報の保護ユーザーのロール（全体／自荷主のみ／自デポのみ／禁止）によって、APIはアクセス可能なスコープを絞り込む。「お知らせ」のアクセスすべてが対象となる（APIの実装修正で実現）
画面上の保護ユーザーのロール（禁止）によって「お知らせ」エリアの表示制御を行う（コンポーネント認可基盤を使用する）
既存の作りへの合わせ方ログインユーザーの権限グループごとにアクセス可否・範囲（全体／自荷主のみ／自デポのみ／禁止）を管理する既存の権限項目と同じ考え方に揃える。
前提（基盤に委ねる）ルート保護・権限判定の実行時の仕組み・API側の絞り込み処理そのものは、別途整備される認可基盤に委ねる。本チケットはその基盤に「お知らせ一覧」用に設定すべき内容（ロールごとの許可範囲）を確定することが目的
スコープ外（やらないこと）:
  • 権限判定基盤・ルートガード・API認可処理そのものの実装
  • お知らせ一覧の列構成・ページング件数・ソート順など表示フォーマットの変更（今回はロールによる出し分けのみ）
  • お知らせ登録画面（掲載対象の設定UI）の変更（下記論点で扱うのみ。対応要否は別途判断）

要確認事項（合意が必要な論点）

各論点は現状値を提示済み。回答欄に記入してください。

#論点現状回答
1「自荷主のみ」ロール（OEM先運用管理者〈管理者用〉、KSL運用管理者）は、「掲載対象デポが、そのユーザーの所属荷主に属するデポであれば表示」という間接判定でよいかお知らせの掲載対象は「デポ」単位のみ設定でき、「荷主」を直接指定する項目は無い☐ Yes ／ ☐ No
2「非表示（禁止）」ロールでトップメニューを開いた場合、他パネル（帳票作成通知・デポ掲示板等）は通常表示され、お知らせエリアだけが非表示になる理解でよいかお知らせエリアは全ロール共通で常時表示される専用セクション（他の切り替え式パネルとは別枠）☐ Yes ／ ☐ No
3コールセンターオペレーター（地域配送CC委託先用）は社内ロール同様「全件表示」でよいか（委託先でも掲載対象による絞り込みは行わない）マトリクス表では「許可」と明記☐ Yes ／ ☐ No
4複数デポ・複数荷主に所属するユーザーは、いずれか1つでも掲載対象に一致すれば表示される（OR判定）理解でよいか―☐ Yes ／ ☐ No
5「自デポのみ／自荷主のみ」ロールに所属デポ・所属荷主が1件も設定されていない場合の挙動は0件表示で良いか―☐ Yes ／ ☐ No

完了条件（受け入れ観点｜目的トレース）

各項目を1件ずつ確認してチェックする（全項目が完了でマージ可）。テストデータは下記「テストデータ設計と期待表示マトリクス」を用いる。チェックの際は、エビデンスとしてスクリーンショットと、実際に用いたユーザーの「ユーザーID」を各項目に追記してからチェックすること。

  • 【全件】U1（全件ロール）でログイン → 掲載期間内の全お知らせ5件（N1・N2・N3・N4・N6）が表示される
  • 【自デポ】U2（自デポ{D1}）でログイン → N1・N4の2件のみ表示され、N2・N3・N6は表示されない
  • 【自荷主】U3（自荷主{S1}）でログイン → N1・N2・N4・N6の4件が表示され、N3は表示されない
  • 【複数所属OR】U5（自デポ{D1, D3}）でログイン → N1・N3・N4・N6の4件が表示される
  • 【禁止】U4（禁止ロール）でログイン → お知らせエリア自体が表示されない（他パネルは通常表示される）
  • 【未設定は0件】U6（自荷主・所属未設定）でログイン → お知らせエリアは表示されるが中身は0件
  • 【添付ダウンロード】表示可能なロールでN4を開く → 添付ファイルをダウンロードできる
  • 【掲載期間ガード】どのロールでもN5（掲載期間外）は表示されない
テストデータ設計と期待表示マトリクス

「許可（全件）／自デポのみ／自荷主のみ／禁止」を一意に判定するためのテストデータ。下の期待表示マトリクスが唯一の合格基準とする。

関係の前提

  • お知らせ ↔ デポ: 多対多（1つのお知らせに複数の掲載対象デポを設定できる）
  • デポ → 荷主: 多対1（デポは1つの荷主に属する）
  • ユーザー ↔ デポ / ユーザー ↔ 荷主: いずれも多対多
  • 判定: 自デポのみ＝「お知らせの掲載対象デポ ∩ ユーザーの所属デポ」があれば表示／自荷主のみ＝「掲載対象デポの荷主 ∩ ユーザーの所属荷主」があれば表示

この設計が保証すること（切り分けの根拠）

  • N2: U2(自デポ)✗・U3(自荷主)✓ → 「自デポ」と「自荷主」の取り違えを検出（D2はS1配下だがU2の所属デポではない）。
  • N3: U1(全件)のみ✓・U3(自荷主S1)✗ → 「全件」と「自荷主」の混同を検出。
  • N6: 1件のお知らせが複数デポ・複数荷主にまたがるケース。U2(D1のみ)✗・U3(S1経由でD2に一致)✓・U5(D3を所持)✓ → 交差判定とOR判定（論点4）を同時検証。
  • N4: 表示可能な各ユーザーで添付ダウンロードまで確認。
  • N5: 全ロール✗ → 権限と独立した掲載期間ガードの維持。
  • U4 と U6 の違い（重要）: 表示件数はどちらも0だが意味が異なる。U4（禁止）はお知らせエリアごと非表示、U6（自荷主・未設定）はエリアは表示されるが中身が0件。テストではこの2つを取り違えないこと。
