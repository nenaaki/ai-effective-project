# 2026-09-17 結合テストAI化：何を作るか

出典：PWテスト担当から受領した結合テスト3日分（2026-09-08〜09-10）のClaude Codeセッションログの分析。

結論：今回作るのは1つ。テストの情報を保持できるスクリプトのフォーマットを決め、実施したものをその形で残す。OKは緑で固定し、NGは赤のまま残す。

## どこへ向かうか

- いま：すべてAI実施。125件にBash 1,448回。実施しても何も残らず、2回目も同じ額を払う
- 今回ここ：メタ情報を持つテストスクリプトのフォーマットが決まり、AIが実施したものがその形で残る。2回目以降はCIが回す。NGは赤で残り、直れば緑に変わる
- その次：残す／消すの判断が回り、本数が経路と異常条件の数に収束する。9画面から53画面へ広げる
- さらに先：実施の起点が仕様書・テストケースの更新になる。AIは差分だけ実施し、残りはCIが回す。規約が他案件へ持ち出せる形になる

4章「今回やらないこと」は、捨てたのではなくこの先に置いたものにあたる。

## 1. 実施したテストをスクリプトとして残す

- WHAT：AIがテスト実施したケースをスクリプトとして書き出す。「スクリプトのメタ情報」がテストケースの内容と結果の記録となる。書き出しは実施の副産物として出し、人間の工程から外す
- WHY：1回目は125件の実施にBash 1,448回を要し、2回目にあたるWebKit再実施25件は同じ額を払って25件すべて判定一致だった。成果物がコードでないため2回目以降の単価が下がらない。回数が出るのは再テスト側であり、そこが毎回AI実施ならコストは永久に下がらない
- 線引き：経路の妨げの観察は初回のAI実施が担い、スクリプトは確定した期待値の固定に使う
- 今回のスコープ：ディレクトリ構造とフォーマットの決定、テストの実施と結果の自動集積

### テストスクリプトのディレクトリ構造とフォーマット自体がテストの情報を持つ

台帳・報告書・証跡に散っている情報を、スクリプト1ファイルに寄せる。別の管理表を作らない。
この構造はGitHubに保存し、誰でも実行できる。

- ディレクトリ構造：Open-Knowledge-Format構造
- 先頭：テスト仕様
- description：テストのタイトルとケースID
- 末尾：例外が出た箇所と実測値をコメントとして追記する。末尾に足すので行番号がずれず、落ちた箇所の参照が実行をまたいで生きる
- 追記の粒度：赤→緑、緑→赤の遷移が起きたときだけ1行。毎回の実行結果は別ファイル（jsonl）に出し、ソースには積み上げない

この形にすると3つが取れる。

- 失効の検出が機械的になる。先頭コメントは台帳の期待値の写しなので、台帳と突き合わせて差があればそのテストは失効。AIが解釈して判断しなくてよい
- 台帳への転記が要らなくなる。description にケースIDが入っていれば、CIのレポートがそのままケースID単位の結果一覧になる
- 直ったかどうかが末尾の遷移記録で分かる。人が再実施して確かめなくてよい

### OKもNGもスクリプトを残す

- 直ったかどうかの確認が自動になる。今はNGを文章と証跡pngで渡していて、直ったかの確認はまたAI実施。赤→緑の遷移で判定できる
- 赤を出せるスクリプトは、何かを検証していることが実証済みという意味になる。OK確定ケースだけを書き出すと全部が緑で、そのスクリプトが実際に何かを見ているのか確かめる手段がない
- 対象外：原因がテスト側・環境側にあるもの（データの日付ズレ、起点URLの誤り、ネットワーク事象）。製品を検証しないのに赤を出し続ける。今回のNG 61件のうち31件がこれにあたる

## 2. どう回すか

AI実施 → 実施したその場でスクリプトを書き出す（OKは緑、NGは赤） → 以降はCIが回す → 赤が緑に変わったら末尾に記録される → 仕様が変わったものは人間の判断で削除して起こし直す

- AI：実施と判定、スクリプトの書き出し
- CI：スクリプトの実行と証跡の記録
- 人：失効の承認

## 4. 今回やらないこと

- スクリプトを残す／消すの判断とその運用。まず残す側に倒し、本数の整理は実績が出てから行う
- 仕様更新・テストケース更新・実装変更の3系統に対する同期エージェントの新設。
- 正本不一致の是正。不一致の検出はテスト側で行ってよいが、是正は仕様側の課題として別に立てる。正本が5系統に散っている状態はテスト側では解けない
- ルール群の汎用化（AI結合テスト実施規約）とエージェント一式の実装。53画面のうち実施済みは9画面で、この段階では早い。スクリプト化が回ってPWで実績が出てから着手する
- 隔離・独立判定の定式化、並行可否の自動導出、実行前ゲートの自動化、委譲プロンプトのエージェント化。いずれも価値は認めるが今回の対象外とする

## 5. 残っている論点

- 承認者：スクリプトの失効を誰が承認するか
- 評価指標：人の台帳との一致率を精度指標として使い続けるか。経路の妨げルールを適用するとAIのほうが仕様に忠実でも減点される
- スクリプトへ固定する時期の判断基準：OK率39%の段階で固定すると仕様変更で落ち続ける
