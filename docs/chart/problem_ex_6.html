課題事例⑥: AIの「最後の2%」修正の属人性

AIDD 試行の構造的課題 / 2026-07-16 社長との会話 ＋ 熟練者の暗黙知を抽出 / 2026-07-20 更新：抑止＋対応の「両輪」に整理

2%はゼロにできない → 抑止と対応の「両輪」

課題と論点

課題
AIが98%正しく作っても、残り2%を100%にする工程は必ず発生する。
この工程の 属人性（＝30分かかる・人が直すと壊れる）をどう無くすか。
論点
1
「30分かかる」と「人が直すと壊れる」は別問題か
2
属人性はどこに宿るか（AI側か・人間側か）
3
抑止（出さない工夫）だけで足りるか
発見
「30分」と「壊れる」は同じ現象の裏表。指示の3点セットが欠けると、AIは全体を探索し(=30分)、契約を誤解して実装をいじる(=壊れる)。
結論① 属人性の正体
人間側正体はAIへの指示スキル（暗黙知）。同じ2%でも熟練者は30分かからない
結論② 打ち手は「両輪」
両輪抑止で出す量を、対応で出た後のコストを下げる。2%はゼロにできない前提

残差2%を仕上げる「型」（暗黙知の抽出結果）

2つの「手」の使い分け

鍵
熟練者は毎回「場所・あるべき姿・証拠」の3点セットを渡している。これが揃うとAIは契約ごと理解を更新し、周辺を壊さない。抑止・対応どちらの土台にもなる。
指示する ── あるべき姿が分かるとき
場所（どの層か）＋ あるべき姿（＝契約）＋ 証拠（スクショ・正本・期待値）
詰問する ── 実装が怪しいとき
仮値実装などに「なぜそうした？」と問い、AIに誤った前提を吐かせてから直す。破綻の根本原因を先に潰す。
層ごとの指示の例
見
正本/モックのスクショを添付し「〇〇は××であるべき」
API
「仮値に見える。APIから正しく取得しているか確認・修正せよ」
DB
「どのテーブル/カラムが画面に出ているか確認させる」

型の②③をAIに肩代わりさせる（レイアウト以外＝全部データ経路）

採用する仕組み（初回実装のゲート）

切り分け
レイアウト問題（→事例②のスクショ突合）を除けば、2%はすべてデータ経路の問題。人がやっていた②③をAIに肩代わりさせる。
実装AI＝自己申告
安い作った本人が経路を表で申告（画面項目→出所→table.column→実データ?）
レビューAI＝敵対的検証
疑う申告を鵜呑みにせずスキーマ(SSOT)・実APIと突合。幻覚・モック由来の固定値を弾く
仮値ルール（DB非依拠は有罪推定）
DBに基づかない値は原則NG。table.column まで辿れない値は理由を問わず却下（無罪推定でなく有罪推定）。特にモック由来の固定値に注意（モックはレイアウトの正本だが値は偽物）。出所不明なら停止し「何が足りないか」を率直に報告。
限界
このゲートが見るのは「DBに辿れるか」だけ。値が業務的に正しいか・振る舞い・違和感はすり抜ける → タブ4「対応」へ。

出た2%を「速く・壊さず」直すループ

出た後を型にする

前提
どれだけ気を付けても2%は出る。抑止だけに振らず、「出た後」も型にする。抑止で量を、対応でコスト（30分・壊れ）を下げる両輪。
抑止をすり抜ける2%
A
契約自体の誤り（要件誤解）— 経路は正しいが「あるべき姿」が違う
B
振る舞い・異常系・状態遷移— 単項目は正しいが組み合わせで崩れる
C
レイアウト崩れ（→事例②）／ ④違和感（言語化前でゲートにかからない）
結論③ 速く・壊さず直す
検知出口検収で捕まえ、3点セットで指示（＝発見1の裏返し）
ループ修正後に経路報告を再実行。抑止を初回だけにせず各修正にも巻く
結論④ 社長案の活かし所／限界
脱出弁「別AIに分けよ」は30分が続いた時の仕切り直しとして吸収
①④のみ人に残るは習慣と違和感だけ。ただし完璧にはならない
