OWNERPR本文のテスト項目は誰が埋めるか

pr-writer が空のチェックリストを作り、各 tester が自分の担当ラベルの行だけを部分編集で埋める。担当の無い項目は作らない（誰も埋めないまま残るため）。

担当ラベル埋める tester対象ID書式
APIbackend-testerGraphQL 実呼び出し・DB確認・エラーコード・jest / tscT-*
画面frontend-tester新規実装画面の受け入れ（モードT / S）・next buildT-*
デグレfrontend-regression-tester変更が波及する既存画面（REG カテゴリ中心）R-*
人手人間複数画面をまたぐ業務操作など自動検証でカバーできないものT-* / R-*

pw-dms チケット駆動サイクルを I/O 視点で図示。現行フローの要点は3つ — ①test-spec-designer は既定ステップで、実装より前に「現行ベースライン（prisma/DTO/schema.gql）⊕ 変更指示（完了条件/brief/要件定義書/spec）」から期待結果を確定する（実装後の DTO/prisma は参照しない。飛ばす場合は理由を1行記録する）。②デグレ検証は frontend-regression-tester に分離され、frontend-tester は新規実装の受け入れ（モードT/S）に専念する。③PR本文がテストの単一の真実で、テスト実施前に pr-writer が安定ID・担当ラベル付きの空チェックリストを作り、各 tester が自分の担当行へ結果と証跡を書き戻す。加えて、あらゆるエージェント起動にはオーケストレーターが関連ナレッジ（knowledge/ の concept パス）を添える（該当なしなら「なし」と明示）。最後のセッション分析がセッションログから「実装したものの情報」と「実装時に人間とやり取りが必要だった部分」を knowledge/ へ書き戻し、次チケットの入力として還流する（サイクルが閉じる）。旧フローの図示は比較のため据え置き。議論用ドラフト。

「このチケットで作るもの」を中心に置く。テスト成果物は 3 層でこれを覆う。層ごとに担当・入力・覆う範囲が違う。

CENTERスコープを中心に、3層で覆う

外側｜変更が波及する範囲regression-scope問い: どこをテストするか

スコープの外まで覆う。仕様どおりかではなく、作ったせいで壊れうるものを差分から機械的に洗う。共有資産を触ったら利用箇所を grep で全列挙し1件ずつ項目化する。

元にするもの: git diff（実装後）／ specs/** ／ 共有資産の利用箇所 grep
出力: regression-scope.md 8カテゴリ別チェックリスト カバレッジ自己診断表 PR本文では R-* 項目
内側｜このチケットで作るデルタtest-spec-designer問い: どんなケースで叩くか

スコープの内だけを覆う。完了条件を 前提 → 入力 → 操作 → 期待結果まで確定した実行可能なケースにする。波及（デグレ）は扱わない。

元にするもの: 変更指示（完了条件・brief §7・要件定義書・spec §5） ⊕ ベースライン契約（現行 prisma / DTO / schema.gql）
※実装したデルタのコードは読まない（なぞりを避ける）
出力: test-spec.md §3 ケース表 §6 トレーサビリティ（完了条件↔ケース） 要確認事項（差し戻し） PR本文では T-* 項目
核｜完了条件・受入基準pm問い: 業務として受け入れるか

「作るべきもの」の合意そのもの。内側のケースはここへトレースされ、pass ケースが1件も無い完了条件は ❌ 未充足として出る。

元にするもの: 合意目的（業務語）
出力: pm.ticket.md（完了条件・受け入れ観点）

重なって見えるときの区別

変更した画面は両者が触れる。内側＝受入基準どおりか／外側＝層ごとの観点が最低1つ立っているか。問いが違うので片方では足りない。

要点は「テストケースの出どころを分けたこと」。内側は実装前に完了条件から期待結果を確定し、外側は実装後に差分から波及を洗う。出力先が違うので互いに上書きせず、PR本文で1本に合流する。議論用ドラフト。

AI の解釈ズレを人間が是正したやり取りを、ナレッジベースに記録として積む。次のチケットの仕様精査でそれを引き出し、Spec 出力時に「注意すべき点」として先回りで刷り込む。

LOOP是正のやり取りを、次の Spec に先回りさせる

今回のチケット記録する
1AI が Spec を解釈して実装する
2解釈がズレる（意図と違うものが出る）
3人間が「そうではない、こうだ」と指示して修正させる
4セッション分析がセッションログから抽出する
▼ セッション分析が積む
▲▼ 仕様精査が引き出す
次回のチケット効かせる
5仕様精査で、関連する記録を引き出す
6Spec に「注意すべき点」を書いた状態で AI に渡す
7AI は同じ取り違えをしない
8人間の是正指示が減る＝デバッグが軽くなる
ナレッジベース（knowledge/）チケットをまたいで残る

1回限りの暫定判断は積まない。繰り返し参照される確定知識だけを concept として残す（source: PW-XXX）。

実装記録何を・どう作ったか。仕様変更時に「どこに効くか」を追える as-built の解釈。
誤解と是正の記録AI がどこを取り違え、人間がどう直させたか。次の Spec に書くべき注意点そのもの。
↺同じ誤解を2度させない — 是正のやり取り自体が、次の Spec の材料になる
デバッグを「その場で直して終わり」にせず、誤解の型として残すのが要点。人間の是正は Spec の不足を指し示しているので、それを次の Spec の前提に織り込めば、同じ往復が繰り返されない。議論用ドラフト。
