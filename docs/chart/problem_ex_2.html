現状フロー（モック適合チェック）

通常業務 画面と mock が一致しないときの一般的な対応
mock を正とする場合、同様の構造になるよう 修正を続ける。
（目視で差分を確認 → 実装を修正 → 再度突き合わせ、を一致するまで繰り返す）

課題と論点

課題
モックと同一の画面が作られないケースがある
現状
planner が mockup から skeleton.tsx を抽出 し、コンポーネント階層（セクション数・フィールド数・列数）の理解は引き継いでいる。 一方で skeleton には grid 配置・1 行あたりの密度・横並び/縦並び といったレイアウト情報が落ち、engineer は app-admin 共通基盤（DrawerCard 等）の都合でそれを再現せず実装する。 tester は 視覚比較を画像で行えず静的解析に代替 しているため、見た目の乖離を検出できない。
論点
1
ユーザーが mock 画面のキャプチャを与え、それと実装の比較を行う
2
AI が 自動で対象画面のキャプチャを取得 し、mock キャプチャと比較する
3
mock の 構造把握を強化 する（skeleton にレイアウト情報を残す等）
結論 / UI における AI 活用方針（実用性優先）
現案件方針
モックは顧客と 1 つずつ丁寧にすり合わせ 済み。技術的に無理でなければモックの画面構成を「正」 とする
万能化否定あらゆる要望を AI で自動解決する「万能テンプレート」は工数増。追求しない
実用性重視美しさより業務道具としての実用性（連打しやすさ等）を優先
手作業へ切替定型 7〜8 割は AI 任せ、主要画面は 人間 / 対話型 AI で調整。「すり合わせフェーズ」を正式工程化
仕様変更提案AI 生成で十分な場合は上流に「このままで良いか」確認し、修正工数自体を削減
