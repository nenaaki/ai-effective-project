# 設計をどこで詰めるか（実装前に詰める型 / 実装後に突き合わせる型）

- 報告：実装前に詰め切ってリバースで確認する型がCSV非同期出力のケースで実証できた
- 報告：データモデル変更とインフラ制約はエンジニアのキャパを超える
- 方向性確認：実装後に突き合わせる型で進める方向に違和感はないか

## 報告：実装前に詰め切ってリバースで確認する型がCSV非同期出力のケースで実証できた

- 先週採用したのは「実装前に設計を詰め切ってから作らせる」と「実装内容から設計図を再出力して人間がレビューする（リバース）」の組み合わせ（以下 pre-design 型）
- CSV出力を既存の非同期出力へ組み込む作業は、最後まで pre-design 型で乗り切れた
- 既存コードがある改修でも、前提を書き切れれば実装前に詰め切れると言える

## 報告：データモデル変更とインフラ制約はエンジニアのキャパを超える

- 開発中期以降のデータモデル変更は影響が横断し、前提を書き切れない
- インフラ制約が絡むものも同じで、前提と例外が幾何級数的に増える
- 増えた前提には重複や矛盾が混ざり、AIがそれを真に受けて誤った設計やバグを生む
- 矛盾なく書き切る作業が人間側の限界を超え、pre-design 型だけでは支えられない

## 方向性確認：実装後に突き合わせる型で進める方向に違和感はないか

- 内容：実装前の設計は軽くし、実装後に「仮実装 → 設計を逆算 → 人が指摘 → リファクタ」を2〜3周回して詰める（以下 post-design 型）。今は前提を書き切れないカテゴリに限って試行中
- 仮説：先に仮実装をAIの思うままにさせた方が、トータルの時間は短いのではないか
- 検証：メッセージ基盤で両方の型を回して正確に比較する（pre-design で設計を起こしきれる規模でありながら、どちらで作っても最後は同じ形に整うと考えられるため）
- 確認：この方向で進めて違和感はないか（周回上限と離脱条件は要設計）
