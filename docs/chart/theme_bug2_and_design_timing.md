# バグ2%問題と pre-design / post-design — これから何をすべきか

出典: 課題事例⑥・⑧、議事まとめ 2026-08-13・08-20・08-26・09-03 ／ 作成 2026-09-09

結論: 残る2%はデバッグに集中。摘出を機械化して人の判断を2か所に絞り、詰め切れないカテゴリは post-design に振る。9〜10月の主題はこの振り分けを含むハイブリッド確立。

## 論点1: 逆方向探索に足りない3つを実装する

- WHAT: 順方向に「判断を書いた先の位置の併記」「不明点ID」、逆方向に「探索スクリプト」を足す。
- WHY: 到達はできるが、辿り方がAIの推測依存。上限なく探し直し、外れれば誤結論に着く。
- HOW: 入力はコード1行かテストID。誰が・何を見て・どの正本に従い・何が未解決かを1枚で返す。

## 論点2: 人が決める箇所を2つに固定する

- WHAT: 「仕様不備」「人間判断の仮実装」「AI独断」の3種に断定させる。
- WHY: 材料の中だけの狭い推論に閉じれば、当て推量が消える。属人性は判断側だけに残る。
- HOW: 人は「仮実装か仕様修正か」「仕様の確定」のみ決める。手を動かすのは常にAI。

## 論点3: デバッグを原因調査に絞る

- WHAT: 原因調査のみを機能ブロックにし、修正指示と実行は切り離す。
- WHY: 修正は変更要求の反映と同一。MECEでない構成は経路で取り違える。
- HOW: 修正は新規機能開発ルートを呼ぶ。環境ゲート → 問診ゲート → 層のバイセクト。

## 論点4: 原因は要求情報側から潰す

- WHAT: (a) 仕様情報の不備 と (b) 実現方法の選定不良 に切り分け、(a) を先に潰す。
- WHY: (b) は従属変数で、(a) が直れば結果的に直る確率が高い。
- HOW: 「期待値はこれ、結果はこれ」を投入し、直すべき仕様をAIに先に出させる。

## 論点5: pre / post の振り分けを着手前に決める

- WHAT: タスクごとに、実装前に詰め切るか、作らせてから突き合わせるかを決める。
- WHY: 順方向は前提が幾何級数に増えて頭打ち。矛盾を真に受けたAIが設計とバグを生む。
- HOW: 物差しは前提を書き切れるか・既存コードの有無・横断範囲。判定者は未決。

## 論点6: pre-design は壁打ちを工程に確保する

- WHAT: 実装前にUML図を出させ、疑問点をぶつけ合ってから実装に入る。
- WHY: 369MBでLambda制限超過の事例は、入出力ではなく取得経路の前提が欠けていた。
- HOW: 壁打ち4時間で一発パス・手戻りゼロ（従来2日以上）。時間を見積もりに明示する。

## 論点7: post-design は収束判定と離脱ルールを持つ

- WHAT: 仮実装 → 設計を逆算 → 人間が指摘 → リファクタのループに、離脱条件を入れる。
- WHY: 2〜3周で着地した実証はあるが収束保証はない。破綻を完成と勘違いするのが最悪。
- HOW: 「収束しなければ人手の設計開発に戻す」検出パスをスキルに実装。周回上限は未決。

## 論点8: 責務分割を計画時に織り込む

- WHAT: エージェントの責務範囲を分割し、コンテキストを一点集中させない。
- WHY: 住所形式の変更が取込やAPIへ波及し、一括依頼では拡大解釈を起こした。
- HOW: 分割・並列化でバグ波及と同一ファイル重複参照が減り、ロス時間を削減できた。

## 論点9: スキル化は適材適所で判断する

- WHAT: 複雑になりそうなタスクは、事前のスキル作成をあえて後回しにする。
- WHY: 全部をパターン化するとスキル作成だけで破綻する。
- HOW: pre-design で押し切れるものから型にし、post-design 側は知見が溜まってから。

## 残っている論点

- 探索スクリプトの実装と、位置併記・不明点IDの運用定着。
- 収束判定のしきい値（何周で人手へ離脱するか）。
- pre / post の判定を、登録時点で誰がどう決めるか。
- 2% → 0.2% を何で測るか。
