# イテレーション3 の成果と課題

出典：議事まとめ 2026-09-03 / 09-08 / 09-09 / 09-10 / 09-17、イテレーション3 タスクデータ（2026-09-16 時点）。

結論：出来高は計画を上回り実工数は下回った。ただし成果の出た理由（夜間のAI稼働）を今の測り方が表現できておらず、人の詰まりどころは実装からレビューへ移った。

## 成果と関連課題

- 計画の 2/3 程度の期間でイテレーション３を完了
  - 進捗が測れていない。夜間ループは複数チケットをまとめて流すため、稼働をタスク単位に切り分けられない。
    - いっそ、AI＋人、AIで別々の線を引いてみるのも手か？
    - AIが「自発的に割り当てられたチケットを開始」できても良いような気がする。（人間の判断が要るタイミングで情報を人間に戻し、別のチケットの作業を進めていくなど）
- エージェントの責務を分割して並列化できるようにした。結合テストのスクリプト生成・管理
  - PM承認前工程（PMがボトルネックの場合あり）
  - 設計工程（設計レビューは人がボトルネック）←設計レビューを自動化する方法をイテレーション４のタスクとしたい
  - 実装・レビュー・テスト設計工程（並列）
  - テスト・デバッグ工程（PC1台で1タスク。ボトルネック化している）←テスト設計の品質が良く、精度は非常に高い
  - PR
- バグ2％問題：順設計・逆設計の取り入れによる、デバッグ精度の向上と自動化
  - 3度回してダメな場合はAIはその段階で人の助けを求める形にした（イテレーション３で本件は一旦クローズ）
- 開発環境とトークンの問題の対策
  - 設計資料を HTML から Markdown + Mermaid へ変更し、実装からのリバース設計のトークン枯渇（2回発生）を緩和。
  - テストフェーズで環境が不安定化（WSLがハングアップするなど）について調査と対策を実施した。（かなり安定した）

## 課題

- 結合テスト不具合の解消など、比較的軽いタスクのテストに時間がかかっている。（人間ならすぐに直せるものがなかなか終わらない）
  - デグレチェックが厳密すぎるのかも。（軽量修正モードの検討中）
- ボトルネックが2つ
  - 人のボトルネックがレビュー・確認へ移動。←次に自動化すべきはレビュー工程
  - AIのテストフェーズがボトルネック。Webアプリの場合ポートの都合で1台で1ラインしか走れない。
    - 2台目のPCを申請することは問題ないか？
- 結合テスト・シナリオテストについて、AIを使いながらもAIのテストをさせているだけで成果を捨ててしまっている（PWのテストチーム）
  - テストをスクリプトを捨てない方向へ。運用上のルールと仕掛けを整備する必要がある
- 結合テストの不具合のうち、AI駆動原因のものとそうでないものを分類して、人間の作業と比してどうであるかを計測すべきか。
