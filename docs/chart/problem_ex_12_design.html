配送管理システム · アーキテクチャ設計

PDF生成基盤設計

配送指示書 PDF をデポ単位の ZIP にまとめ、期限付き URL で渡す仕組みです。 受付と生成を切り離してあり、帳票定義を1件足せば新しい帳票へ広がります。

実装済み · デプロイ前

設計原則

01 受付と生成を切り離す 要求を受けたら即座に応答を返し、生成は裏で走らせます。画面は状態を見に行くだけです。
02 業務データのやり取りは api-core に集約する 画面もワーカーも、読み書きは API Gateway 経由で api-core に依頼します。業務ルールと権限が1か所に集まります。
03 重い処理だけをワーカーへ PDF 生成が積むのは Chromium・テンプレート・フォントだけ。業務ロジックは持ちません。
04 成果物は S3 へ直接、状態は api-core 経由で 出力ファイルは S3 へ直接書き、状態と保存先だけを api-core に書き戻します。
05 権限の範囲を超えて見えないファイル構成で出す 「自デポのみ」の人に他デポの情報が渡らないよう、ファイルの区切りを権限の区切りに合わせます。またぐなら分けて出します。
06 認証の形態で住み分ける 画面用は Cognito JWT、ワーカー用は内部 API キー。ガードが別なので取り違えません。キーはシステム内で1つ。
07 仕事は「積む」、ワーカーは「引き取る」 api-core は「生成待機中」で積むだけ。ワーカーは対象を指定されずに起動し、古い順に1件ずつ引き取ります。
08 仕事が無くなればワーカーは終了する 引き取れる仕事が無くなった時点で終わります。常駐しないので、動いた分だけで済みます。
09 引き取りは楽観的排他制御で行う 「生成待機中」→「生成中」の更新に勝った1つだけが進みます。負けたワーカーは別のレコードへ移るので、二重に作られません。
10 並列数は「生成中」の件数で抑える 起動時に「生成中」を数え、上限（仮 10 件）に達していれば起動しません。積まれた仕事は稼働中のワーカーが拾います。
11 進捗を書き、止まったものはタイムアウトにする PDF 1枚ごとに生成済み枚数を書きます。これが進捗表示と心拍を兼ね、更新が1分途切れた「生成中」はタイムアウトエラーになります。

1. 生成の入口は2つ、起動口はひとつ

入口は画面からの手動要求と、取込完了後の自動要求の2つ。 どちらも api-core の受付を通るので、ワーカーを起動するのは常に api-core だけです。

3. 多重生成と無尽蔵な並列化を防ぐ

ワーカーは対象を指定されずに起動し、自分で仕事を探します。仕事は「生成待機中」で積まれ、 引き取られて「生成中」になります。これで3つの心配が片付きます。

  • 勝手な起動。 「生成待機中」を積めるのは api-core だけ。不正に起動されても何も見つからず終了します
  • 多重生成。 引き取りは楽観的排他制御なので勝つのは1つだけ。再試行があっても同じ帳票は作られません
  • 無尽蔵な並列化。 起動してよいのは「生成中」が上限（仮 10 件）未満のときだけ。積むことと走らせることを分けてあるので、 要求がいくつ届いても走る本数は頭打ちになります。あふれた分は待機したまま残ります
タイミングやること
受付 結果レコードを「生成待機中」で作ってコミットする。この行の作成時刻が基準時刻になる
起動判定 「生成中」を数え、上限（仮 10 件）未満のときだけ起動する
引き取り 「生成待機中」を古い順に1件選び、楽観的排他制御で「生成中」へ更新。更新に勝った1つだけが帳票 ID と生成に要る文脈を受け取る。負けたら別のレコードで再試行
処理中 PDF 1枚ごとに生成済み枚数を書き戻す。その行がまだ「生成中」であることを毎回確かめ、そうでなければ拒否する
異常時 更新時刻が1分以上前の「生成中」は「タイムアウトエラー」とする。件数を数えるときと引き取りのときに合わせて判定すれば、別に監視を置く必要はない
完了 「完了」に更新する。以降は「生成中」でなくなるので書き戻しは通らない。ワーカーは「次の仕事はあるか」に戻る
終了 引き取れるレコードが無ければ「仕事なし」が返り、ワーカーはそこで終了する

ワーカーに Function URL やイベントソースは付けません。入口は IAM 認証つきの起動1本だけです。

未完了があるときだけ状態を取りに行く

一覧を丸ごと取り直すのは重いので、状態だけを返す専用の APIを分けています。 未完了（待機中・生成中）の行が1件でもあれば5秒ごとにその行の状態だけを取り、全部が終われば止まります。 常時ポーリングにはしません。

これとは別に、一覧そのものを60秒ごとに取り直します。取込や他の人が作った新しい行は 状態の取得では拾えないためです。監視できるのは表示中のページの行（最大100件）です。

行の見え方

指示書再発行は押下で保存まで終わる

生成は非同期のままで、完成を待つのは画面側です。同期の生成 API は持ちません。

観点決めたこと
待ち方1秒ごとに状態を見て、出来たら保存する（上限60秒）。1件は押下から約2〜3秒。複数デポは §13 のとおりボタンを押させる
見せ方ボタンをスピナーにする。複数デポのときだけ (2/3) の進捗を出す
保存の形期限付き URL に attachment を付ける。付けないと PDF はタブ表示になり保存されない
待機中の離脱再読み込み・タブを閉じる操作は引き止める（文言はブラウザ任せで指定できない）。アプリ内の画面遷移は引き止めない（保存は完走する）
保存できなかった分件数を添えて帳票作成通知へ誘導する。生成そのものは残っているので取り直せる

8. 失敗したときに何が起きるか

生成は裏で走るので、失敗しても画面は知りません。結果は必ずレコードに残し、画面と通知の両方から気づけるようにします。

起きたことどうなるか
生成の途中で失敗した その場で理由を書いて「エラー」にする。時間切れを待たないので、原因がすぐ分かる
対象データが1件も無い 空の ZIP を作らず「エラー」に倒す。中身の無いファイルを配らない
ワーカーが黙って止まった 更新が1分途切れたものを時間切れとして「エラー」にする。別に監視は置かず、受付と引き取りのついでに判定する
ワーカーの起動に失敗した 受付は成功させる。仕事は「生成待機中」で積まれたまま残る。画面起点なら、 画面を開いたときと60秒ごとの再取得のときに、待機中があって生成中が無ければ起動する

取込ワーカー側で起動に失敗したときの扱いは取込基盤側の責務です（完了まで見届けるか、利用者へ知らせるか）。

利用者から見えるもの

一覧では「エラー」の行になり、理由はマウスを乗せると出ます（§7）。あわせて通知基盤へも飛ぶので、 画面を見ていない人も気づけます。

9. やり直しについて

いまできるのは画面で対象を選び直して再発行することだけです。帳票作成通知の一覧に 「この帳票を作り直す」操作はなく、失敗した行もそのまま残って別の行が増えます。 この扱いも含めて、まだ詰めていません。

問い背景
作り直したものを「更新分」として区別して見せるか 代引き額が修正された配送について配送指示書を再作成し、デポ単位で「更新分の配送指示書」として掲載する記載がある（FE012 の未反映更新点・要確認のまま）。いまは同じ見え方の行が増えるだけで、どれが最新か画面から分からない
古い行をどう扱うか（残す／消す／並びを下げる） やり直すほど行が増える。保管期限を過ぎたファイルは置き場側で消えるが、行は残る（§10）
エリア洗替のときの再出力は誰が起点か（自動／手動） 洗替でエリアが再割当されると ZIP の分かれ方も変わるため、同じタイミングで帳票を再出力する運用が想定されている。起点の記載はない

商品ショート時に水源を振替えて依頼指示書を再作成する運用も挙がっていますが、フェーズ2以降として確認済みです。

10. 誰が何を見られるか

配送指示書には受取人の氏名・住所・電話番号が載ります。仕組みが回りくどく見える箇所は、たいていこれが理由です。

場面備え
ダウンロード 期限付きの URL を押した瞬間に発行し直す。URL を保存しておいて後から開くことはできない。一覧を眺めているだけでは発行されない
一覧・状態の確認 自デポの帳票しか返さない。他デポの帳票は「無い」ものとして扱い、存在も知らせない
ワーカーへのデータ受け渡し ワーカーは DB を持たない。配送データは引き取った帳票の分だけを api-core から受け取る
保管 置き場は帳票専用のバケット。業務ファイルとも、外部の担当者が触る連携用の置き場とも分ける
期限切れ 保存期限は既定 5 日（環境変数で変えられる）。上げ終えた時刻からの経過で判定し、 過ぎた帳票は一覧・ドロワーとも「ダウンロード」を「保存期限切れ」にして非活性にする。 あわせて期限付き URL の発行も断るので、古い画面から押しても渡らない。 ファイル自体を消すのは置き場側の設定の役目で、行は残る

11. 新しい帳票を足す

帳票1種類につき、帳票種別コードを1つ増やし、定義を2つ書きます。 定義はデータを集める側（api-core）と描く側（ワーカー）に分かれます（プロセスが別なので）。 両方をその帳票種別コードで結び付けます。

どちら決めること
データを集める側 成果物のファイル名／受け取る印字パラメータ／1ページ分をどう取るか（基準時刻より前の有効なレコードを、カーソルで刻んで返す）
描く側 成果物の形（ZIP か単体 PDF か。ZIP なら何で分けて何という名前にするか）／並び順／1行を1ページの HTML にする書き方／外枠テンプレートとフォントの場所

あとは帳票種別コードの一覧と、定義の登録一覧2本にそれぞれ1行足すだけ。 受付から保存・ダウンロードまでの流れは変わりません。

  • 生成の仕組みに帳票ごとの分岐を入れないこと。 書いた時点で足すだけでは済まなくなります。様式の違いはすべて定義側で表現します
  • デポは帳票種別によらず必須です。 中身が配送情報でない帳票でも、ファイルは1デポに属します（§6）
  • 描く側から DB を触らないこと。 足りないデータがあれば、集める側で取ってから渡します

12. 実測値で調整すること

いまの値はすべて仮置きです。実測は基盤が AWS 上にできてから行います。 ローカルは1台のパソコンの上で動いており、並列時のメモリも DB の負荷も本番と違うためです。

先に測るのは3つ

測るもの測り方
A. 1帳票あたりの所要時間 実データ規模のデポ1件で、受付から完了までの時間。エリア数・配送件数と合わせて記録する（件数に比例するのか、それ以外が支配的なのかを見るため）
B. 1帳票あたりのメモリ ワーカー実行時の最大使用量。ヘッドレスブラウザを積むので、ここが1件あたりの重さを決める
C. 1ページ取得の応答時間とサイズ 件数を変えながら、api-core が返すまでの時間と応答の大きさ

そこから設定値を出す

3つは独立ではありません。1ページの件数を大きくすると1回の取得が重くなり、小さくすると回数が増えて所要時間が伸びます。順に決めます。

決める順設定値導き方
1 1ページの件数（仮 100） C から、1回の取得がゲートウェイの応答上限に収まる最大の件数を取り、余裕を見て下げる。ここが他の2つの前提になる
2 ワーカーの実行時間の上限 A（最大のデポ）が収まること。1帳票 ＝「取得の回数 × 1回の時間 ＋ 描画 ＋ ZIP化 ＋ 保存」。収まらなければ、エリア単位へ刻む改修を検討する（§2 の構造は変えずに済む）
3 並列数の上限（仮 10） B × 並列数が実行基盤の割り当てに収まり、かつ同時に走る取得（並列数 × 毎秒の取得回数）を DB が受けきれること。DB 側が先に頭打ちになるはずなので、そちらから決める
4 時間切れの閾値（仮 1分） 正常時の更新間隔の最大値（＝1枚あたりの生成時間の最大）に余裕を掛ける。短すぎると動いている処理を打ち切り、長すぎると異常の検出が遅れる

件数とは別に守る性質があります。「生成時刻 ＋ 主キー」の複合キーで並べ、必ず一意の順序が返ること。 同時刻でも主キーで決着するので、ページ境界でレコードが飛びません。

  • 目標時刻から逆算する視点も要ります。 取込完了後に全デポ分が揃うまでの時間には業務上の目標があります。 デポ数 ÷ 並列数 × 1帳票の所要時間が収まらなければ、並列数を上げるか1帳票を軽くするかの判断です

13. 複数選択がデポをまたいだとき

一覧のデポ絞り込みは任意なので、複数デポの配送をまたいで選べます。ただし 「自デポのみ」の権限の人に他デポの情報が渡ってはいけません（MUST）。 したがって1ファイルに入れてよいのは同一デポ分だけです。

またげるのは全社を見る立場の人だけ

ロールチェックボックス再発行またげるか
デポ運行管理者（2種） ありあり 不可（自デポのみ）
物流本部 Lv.2 / Lv.3 なしあり 不可（複数選択できない）
物流本部 Lv.1 / Lv.4
システム管理者		 ありあり ここだけ可

デポごとに分けて出力する

またいで選んだときは、画面側がデポごとにまとめ直し、デポの数だけ要求を出します （東京3件・名古屋2件なら要求2回・ファイル2つ）。

またいだときは自動で落とさない

複数のファイルを自動で撃つと、2本目からブラウザの複数ダウンロードの許可を求められます （判定基準は時間の間隔ではなく、ユーザー操作から続いているかどうか）。 またいだときは自動保存をやめ、完成した順にデポ名のボタンを出して押させます。 押した分はボタンが消えます。1デポなら成果物は1つなので、従来どおり自動で保存します。

1回の要求で選べる件数

件数はそのまま PDF のページ数になり、生成時間に直結します（配送IDを入れる JSONB 側には実質の制限がありません）。 1回の要求は300件までで、超えた場合は上限を文言で伝え、1件も受け付けません。
