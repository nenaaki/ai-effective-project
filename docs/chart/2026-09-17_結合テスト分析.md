# 2026-09-17 結合テスト分析

出典：PWテスト担当から受領した Claude Code セッションログ一式（`run-info.txt` / メインセッション2本・サブエージェント9本・実施ログ13ファイル177レコード・証跡196枚・2026-09-08〜09-10 実施分）。2026-09-17 議題「2. 結合テストの自動化」の分析結果にあたる。

結論：判定ルールの作り込みは高水準で、そのまま他案件へ持ち出せる資産になっている。一方で成果物がコードでないため再実行コストが下がらず、NGの半分は製品の不具合ではない。

## 1. 前提の訂正

- 聞いていた道具：Playwright
- 実態：`playwright-cli`（対話的なブラウザ操作）であって `playwright test`（テストランナー）ではない
- 根拠：`run-info.txt` に「playwright test は使っていない／Playwright MCP も使っていない／playwright-report・test-results・blob-report は存在しない」と明記
- 意味：「Playwrightでテストコードを書いて回す」のではなく「AIが人間のテスターの代わりに手動テストを実行する」運用。良い点・良くない点の両方がここから出ている

## 3. 良い点

### 3-1. 誤OKを潰す「経路の妨げ」ルール

- WHAT：期待値の達成と、達成までの経路を分けて判定する。手順に無いダイアログが出た／入力値が消えた／ボタンが非活性／2回やり直した／手順外の操作が要った、のいずれかを観測したら、期待値を満たしていてもNGにする
- WHY：自動化は人より速く正確なので、結果だけを見ると「人が実際には操作できない状態」を「できた」と判定する。ルール文書にこの理由が明記されている
- 効果：検証2回目までは誤OKが7件あり、このルールを入れた3回目で1件まで下がった（環境差のみ）
- 評価：AI結合テストの最大の失敗モードを正面から潰している。最も価値の高い発明

### 3-2. 操作ルール【1】〜【7】

- WHAT：`fill` ではなく `type` を使う／入力したら必ず blur する／ポップアップを開くUIは開いてから選ぶ／一覧送りは `press PageDown`／ホバーは段階的 `mousemove`／操作のたびに snapshot でダイアログを確認／別経路で目的だけ達成しない
- WHY：`fill` は value を直接代入してキーイベントを出さないため、1文字ごとの整形・入力途中のバリデーション・maxlength・全角半角変換・インクリメンタルサーチが素通りする。Playwright の自動スクロールは wheel を出さないため遅延読み込みの挙動が変わる
- 評価：E2Eを書く人間が普通にやってしまう手抜きの、ほぼ完全なカタログ。プロジェクト非依存で汎用化できる

### 3-3. 隔離フォルダによるアンカリング遮断

- WHAT：`make_input_folder.py` が台帳をコピーし、人の判定が入るH〜M列と不具合一覧を空にしてから渡す。さらに委譲プロンプトで「このフォルダの外は一切読まない」を課す
- WHY：人の答えを見てから判定すると、AIの判定精度を測ったことにならない
- HOW：終わってから `compare_results.py --ledger` で事後突合する。スクリプト側で強制もしている（資料が欠けたら停止／同種資料が2つあったら停止／前回結果が残っていたら停止）
- 評価：測定設計として正しい。AI判定の精度を語るときの前提条件そのもの

### 3-4. 並行可否を集合演算で定義した

- WHAT：画面Aと画面Bを並行してよいのは `(Aが書く表) ∩ (Bが書く表 ∪ Bが読む表) = ∅` かつその逆も成り立つとき
- HOW：Prismaのサービス層（`this.prisma.tDelivery` 等）まで追って「書く表／読む表」を埋め、マトリクスにした
- 良い点：参照専用の画面でも、他方が更新する表を読んでいれば影響を受ける、まで踏み込んでいる。分からないところを推測で埋めず「不明」として残している
- 実例：FE021商品マスタとFE052再配送依頼は、ケースの中身が「他画面を開いて反映を確認すること」なので並行実施と両立しない、という判定まで出せている

### 3-5. 暴走と誤NG量産のブレーキ

- 1ケース10分でタイムアウトしてNGにし次へ進む
- 妨げが出たら粘らない（別の方法で通そうとしない）
- 到達できないケースが2回続いたら中断して報告する
- WHY（ルール文書の記述）：接続が切れた状態で走り続けると全ケースがタイムアウトして大量の誤NGが出る。「走らなかった」より悪い結果になる
- 評価：AIテストの事故は「動かない」ではなく「もっともらしく大量に間違える」形で来る、という理解が入っている

### 3-6. 「判断根拠」表でAIの推測を全部見せる

- WHAT：報告書に「正本に無く、こちらで補ったもの」という表があり、決めたこと／種別（読替・推論・前例・明記）／根拠／選ばなかった側 を列挙している。加えて「未確認のこと」節
- 評価：AIの出力をレビューする側にとって、これがあるかないかで信頼できるかが決まる。他の資料にも横展開する価値がある

### 3-7. 手順書自身の自己修正が回った

- `SKILL.md` の `type <ref> "<text>"` が実際には動かない（引数1つ）ことを実行中に発見し、エラー文言つきで修正した
- `press enter`（小文字）がエラーも出さず無反応であることを発見し、注意として追記を提案した
- 評価：ドキュメントが実行によって検証されている。AIDDで最も欲しい循環

## 4. 良くない点

### 4-1. 成果物がコードでないため再実行コストが下がらない

- 事実：125件の実施に Bash 1,448回。すべてその場限りの操作で、資産が残らない
- 実例：WebKitで洗い直したとき、同じ25件をもう一度フルコストで流し直した。結果は25件すべて判定一致で、得られた情報はほぼゼロ
- 影響：リグレッションに使えない／CIに載らない／トレースが残らない／リトライできない。`playwright-report`・`test-results`・trace viewer の資産が一切ない
- 位置づけ：今回の最大の損失。1回きりのテストとしては成立しているが、2回目以降の単価が下がらない

### 4-2. NG 61件のうち、製品の不具合は半分以下

| NGの性質 | 件数 |
|---|---:|
| テストデータの日付ズレ（`=TODAY()` 系で当日SQL未投入） | 17 |
| 起点URLの不一致（`/` ではなく `/redelivery`） | 7 |
| 同一原因の連鎖（FE001の日付欄が blur で `2026/01/01` になる） | 4 |
| 環境事象（`ERR_NETWORK_CHANGED` によるセッション切れ） | 3 |
| 小計 | 31 |

- 61件中31件、半分が「テスト対象の欠陥ではない」
- NG理由を文面でクラスタリングすると、上位11クラスタで34件を占める。1つの根本原因が平均3件のNGに増幅している
- 台帳がケース単位で数える仕様のため「前のケースで報告済みでも各ケースをNGにする」ルール自体は正しい。ただし記録フォーマットに根本原因の区別がないため、重複判断のコストが起票側へ丸投げになっている

### 4-3. 人との不一致19%の中身は、精度差ではなく厳しさの差

- 誤NGの実態：FE008の誤NG 5件のうち4件が同一原因（一覧の行押下ではドロワーが開かず、件数セルだけが反応する）。人は件数セルを押して通しOK、AIは経路の妨げを適用してNG
- 評価：AIのほうが仕様に忠実。しかし「台帳との一致率」という指標では減点される
- トレードオフ：経路の妨げルールは誤OKを潰すが、人との一致率を下げる。実測で両方が出ている。評価指標のほうを見直す必要がある
- 唯一の誤OK（FE008-0018）は逆の原因：期待値の項目を1つ見落とした（人は「全体のアコーディオンも開いている」を見た、AIは「16:00~18:00 だけが開いた」で判定した）。期待値が自然文のまま渡され、項目に分解されていないことが原因

### 4-4. 資格情報の漏洩事故が起きた

- 事実：テストアカウントのSTGパスワードが平文で51箇所、Cognitoのトークンが4箇所、ログに残った
- 経路：セッションタイムアウト後の再ログイン時に、パスワード入力欄を含む `snapshot` を取った
- 手順書の状態：`printenv` の出力を貼る経路は警告していたが、snapshot 経由は想定されていなかった
- 影響：ログ一式（計約22MB）全体が機密扱いになり、共有・分析の障害になっている
- 対処：パスワード変更またはマスクの判断を依頼済み

### 4-5. 環境が脆く、失敗の原因を製品に帰属できない

- `ERR_NETWORK_CHANGED` が 9/8 に3画面すべてで発生、9/9〜10 にさらに4回。WSL `networkingMode=mirrored` とVPNの組み合わせが疑われている
- 共有stgのため実施中に他人がデータを変える。FE005で同条件の検索が 19:35 は0件、19:36 は1件を返した
- WebKitが初回は起動せずChromiumで代替し、後日 sudo で `install-deps webkit`（aptパッケージ208個）を実行して解消した
- 評価：テストの失敗が製品由来か環境由来かを切り分けられない状態でテストしている

### 4-6. 正本（SSOT）がない

- 系統：台帳xlsx／画面項目定義書xlsx／テストデータブックxlsx／モック確認用xlsx／Backlogスナップショット の5つ
- 実例：FE024-0042 は、定義書が「CSVダウンロード」、台帳が「Excelダウンロード」、画面にはどちらも無い、の三者不一致
- テストデータブックは画面別に複数冊に分かれ、ルール文書が1章まるまる「どの1冊を開くか」の見分け方に費やされている
- 影響：ケースの正しさ自体が担保されていないため、NGが出ても「ケースが悪いのか実装が悪いのか」を実施者が決められない

### 4-7. 並行可否マトリクスが手作業でスケールしない

- 53画面あるうち調査済みは7画面のみ
- 根拠は `m-product.service.ts` などを読んで人手（AI）で埋めたもの。画面が増えるたび、実装が変わるたびに腐る
- Prismaスキーマ ＋ NestJSサービス層から機械的に導出できるはずの情報

### 4-8. 委譲プロンプトが手書きで60行 × 画面数

- サブエージェント9本のプロンプトのうち約8割が同一のボイラープレート（判定ルール・記録コマンド・分離すべき5項目・報告形式）
- 画面固有なのは「実施するケースと順番」「既に分かっている操作上の注意」「確認済みの実データ」の3ブロックだけ
- 共通部分がプロンプトとルール文書に二重に書かれている（「ルール文書を読め」と言いつつ同じ内容を貼っている）
- 影響：ルールを更新するたびに9箇所＋ルール文書を直す必要がある

## 6. 次に作るものの案（3つ）

### A案：ルール群の汎用化（資料として）

- WHAT：E1・E2・E6・E8 をPW固有の記述から剥がし、「AI結合テスト実施規約」として `docs/` に置く
- WHY：実証データ（誤OK 7→1、一致率81%、1件1.0分、3並列43分）が揃っている今が書く最良のタイミング。他案件へ持ち出せる形にすることが社内展開に直結する
- HOW：Markdown ＋ 図。社長・関係者に見せられる形

### B案：動くエージェント／スキル一式（pw-dms へ移植する前提）

- WHAT：E5のエージェント定義、E4のprecheck自動化、E7のマスキング、E6の根本原因ID を実装する
- WHY：次回のJT実施が実際に速く・安全になる。4-4の事故と4-2のノイズに直接効く
- HOW：成果物の置き場所は別リポジトリ（pw-dms の `.claude/` 配下）になる

### C案：実施の資産化（OK確定ケースのテストコード化）

- WHAT：AI実施を続けたうえで、OK判定が確定したケースだけを `*.spec.ts` に書き出し、2回目以降はCIで回す。書き出しは実施の副産物として出し、別工程にしない
- WHY：4-1が最大の損失。操作の中身はログに全部残っており、テストコードに相当する情報は既に手元にある。コードとして保存していないだけ
- 線引き：経路の妨げの観察は初回のAI実施が担い、specは確定した期待値の固定に使う。役割が違うのでE1の価値は失われない
- しないこと：全ケースをコードへ置き換える全面移行。経路の妨げはAI実施でしか見られない

### 推奨

C は必須。A・B は C の上に積む改善という位置づけで、C → A → B の順。

- Cが必須である理由は3つ。(1) 結合テストは1回で終わらず、回数が出るのは再テスト側。そこが毎回AI実施なら単価が永久に下がらない。(2) AI実施は非決定的で、再テストの道具として不適格（同じ対象で観測が食い違った実例がある）。(3) 一度OKになったものが壊れていないことの確認に、AIの判断力は要らない
- Cは規約の確定を待つ必要が無い唯一の項目。着手が1回遅れるたびに、その回の実施（今回なら1,448回の操作）がまるごと消える
- Aはこのリポジトリの性質（AIDDの効果を説明する資料）に合い、実証データが揃っている今が書くタイミングとして最良。Aで規約を固めないとBのエージェント定義の中身が決まらないため、B は A の後
- Cの未決事項：いつspecへ固定するか。OK率39%、NG 22件は画面がまだ動いていることに由来する。固定が早すぎると仕様変更で落ち続ける

## 相談したいこと

- 進め方：A → B の順でよいか。C（テストコードへの資産化）を先に試す判断もありうる
- C案の可否：PWのテスト工程を playwright test ベースへ移せるか。移す場合、経路の妨げの観点をどう担保するか
- 評価指標：人の台帳との一致率を精度指標として使い続けるか。4-3のとおり、AIのほうが仕様に忠実でも減点される構造になっている
- 4-4の後始末：テストアカウントのSTGパスワード変更の判断（環境担当）。ログ一式の共有範囲もここで決まる
- 4-6の扱い：SSOT不在はテスト側では解けない。仕様側の整備として別に立てるか
